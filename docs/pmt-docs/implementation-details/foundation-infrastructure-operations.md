# 기반·인프라·운영 상세 인계

[상세계획 안내](README.md) · [기능 명세](../function-specification.md) · [원문 계획](../../implementation-plan-v1.md) · [공유 계약·통합](parallel-execution.md).

> 2026-10-01 · 기능목록·기능명세·1차 구현계획 기준의 구현 전 계획이다. 환경·제품 사용 권한·실습 자원은 확인 전이며, 절차 기능은 운영자 실행 및 증거 작성 절차다. 단계 합격은 문서·코드 Test·실습 증거를 서로 구분한다.

## 공통 구현 경계

- G0에서 개발환경을 확인한 뒤 P0부터 준비한다. 개발 PC 측정치를 실습 PC 기준으로 간주하지 않는다. 실습 PC의 CPU·디스크·라이선스는 미확인이다.
- 인프라 8대 구성 검증과 Linux 8대 구성 검증은 각각 별도로 수행하고, 결과와 자원 여유가 확인된 후 각 구성을 4대로 축소한다. 고객 VM과 디스크는 축소 전후 식별·완전성을 대조해 보존 전환한다.
- Linux 서비스 VM은 물리 Hyper-V 호스트에 있고 고객 VM은 중첩 Compute에 있다. VMM 관리 경계가 다르므로 관찰·제어 권한과 증거도 별도로 유지한다. 물리 호스트 한 대의 상시 4+4는 역할별 단일 노드 구성이지 상시 HA 보장이 아니다.
- Galera 검증용 구성과 서비스 MySQL은 별개다. Galera 시험 결과를 서비스 MySQL 복제·전환 합격으로 전용하지 않는다. 정족수, 복제·전환 방식, VPC 기술, executor, MSSQL, IIS, 복구 매체, 자원·보존·복구 목표는 선정·측정 전까지 미정이다.
- 입력·출력은 값의 의미와 공급/수신 주체로만 정의한다. 실제 주소·계정·자원값·기간·목표 숫자·비밀·JSON 예시는 계약과 증거에 넣지 않는다. 런타임 비밀은 승인된 비밀 저장 경계를 참조한다.
- 감사 원장은 업무 변경과 같은 원자성 경계를 사용한다. 앱 계정은 추가·조회만 가능하며 수정·삭제·purge는 분리된 관리 권한과 archive 절차에 둔다. 감사/청구 기록 실패나 용량 부족을 성공처럼 감추거나 조용히 버리지 말고 경보와 명시적 접수 제한으로 드러낸다.
- 백업은 DB 트랜잭션과 고객 VM 디스크의 일관성 관계를 증명해야 한다. 복구는 격리된 대상에서 실제로 검증한다. 릴리스 코드를 되돌릴 수 있어도 스키마가 호환되지 않으면 롤백 완료로 판정하지 않는다.

<a id="fs-001"></a>
### FS-001 실행환경·설정·자원 게이트 확인

- **목적:** 단계별 착수 조건을 증거로 판정하고 미확인 자원에 의존한 작업을 차단한다.
- **추가 범위:** G0/G1/G2별 환경 점검 절차, 확인 항목의 출처·시각·판정·차단 사유를 기록하는 결과.
- **수정 범위:** 이후 단계의 착수 판단은 해당 게이트 결과와 연결한다. 기존 개발 PC와 별도 실습 PC의 인벤토리를 혼합하지 않는다.
- **삭제 범위:** 근거 없는 추정값으로 자원·라이선스·제품 사용 가능을 통과시키는 관행.
- **goal:** 확인된 전제만 다음 단계로 넘기고 미확인 항목을 명시적으로 보류한다.
- **non-goal:** 자원 자동 프로비저닝, 외부 제품 설치, 실제 VM 변경.
- **목표-input:** `gate`는 단계 판정 요청(운영자 제공); `environment_inventory`는 제품·확장·자원·접속 확인 정보(점검 담당 제공); `required_settings`는 단계 필수 의미(계획 제공); `evidence`는 관찰 자료 참조(담당자 제공).
- **목표-output:** `readiness`는 착수 가능 판정(단계 책임자 수신); `missing_items`는 미확인·불충족과 사유(담당자 수신); `verified_inventory`는 실제 확인 항목(후속 작업 수신).
- **구현 동작:** 적용은 P0 준비, G1 실제 연동 전, G2 운영 전이다. 먼저 대상 PC·단계·관찰 출처를 고정하고 제품/버전, 확장, DB 연결 및 테스트 DB, CPU·메모리·디스크, 중첩 가상화, 라이선스, 네트워크·서비스 경로를 항목별로 확인한다. 각 항목은 확인/불충족/미확인의 구별과 근거를 저장하고, 필수 항목이 미확인 또는 불충족이면 게이트를 보류한다. G1에서는 실습 PC 자원을 직접 확인하며 개발 PC 결과로 대체하지 않는다. 확인 과정 실패는 부분 결과와 실패 지점을 남기고 다음 단계 진행 판정을 만들지 않는다.
- **책임·의존 계약:** 환경 점검 담당이 관찰·판정을 소유한다. 점검 항목은 1차 계획의 필수 조건을 사용하며 FS-002의 완료 manifest를 선행으로 요구하지 않는다. 초기 관찰을 FS-002에 제공하고 잠금/호환 확인 후 G0를 판정한다. G1 실제 대상·자원 미정은 해당 실행의 차단 조건이다.
- **코드동작확인 Test방식:** 누락 확장, DB 연결 실패, 오설정, 미측정 자원, 다른 PC의 자료 혼입을 각각 제시한다. 필수 확인이 하나라도 빠지면 진행 가능 판정을 내리지 않는 불변식과, 모든 통과 항목이 출처·시각·대상 환경에 귀속되는 불변식을 확인한다.
- **코드동작확인 로깅방식:** 기술 기록에는 단계·점검 항목 식별·판정·오류 분류·근거 참조·대상 환경 식별만 기록한다. 비밀 연결 문자열·내부 주소는 제외한다. 게이트 사건과 별도 검증 기록의 관찰 근거를 대조해 누락·실패·보류를 구별한다.
- **완료·반환 증거:** 단계별 점검 범위·확인/미확인 결과·근거 종류·차단 사유·후속 의존조건을 반환한다. G0/G1/G2 통과 여부를 각각 기록하고 실측하지 않은 항목은 미확인으로 표시한다.

<a id="fs-002"></a>
### FS-002 의존성 잠금·실행환경 명세

- **목적:** 검증된 런타임과 의존성 집합을 재현 가능한 릴리스 기준으로 연결한다.
- **추가 범위:** 잠금 의존성, 런타임 manifest, 배포물 무결성 및 호환성 판정.
- **수정 범위:** 설치·배포 준비는 G0 환경 확인 결과를 입력으로 받고 R1 배포도 같은 manifest를 참조한다.
- **삭제 범위:** 검증되지 않은 최신 의존성을 무고정으로 설치하는 동작.
- **goal:** 깨끗한 대상에서 동일한 잠금 관계와 호환 런타임을 확인하고 차이를 배포 전에 드러낸다.
- **non-goal:** 현재 미확인 환경에 제품을 설치하거나 버전 선택안을 확정된 사용자 결정으로 취급하는 것.
- **목표-input:** `dependency_lock`은 의존성·버전 관계(저장소/배포 담당 제공); `runtime_inventory`는 검증된 제품·확장 정보(FS-001 점검 제공); `artifact_checksums`는 배포물 동일성 정보(빌드/배포 체계 제공).
- **목표-output:** `runtime_manifest`는 잠금과 실행환경의 연결(배포·검증 담당 수신); `consistency_result`는 일치 여부와 차이(배포 게이트 수신).
- **구현 동작:** 적용은 P0이며 R1에서 배포물과 다시 대조한다. 환경 게이트가 제공한 실제 제품·확장 정보를 수집하고 잠금 의존성을 깨끗한 환경에서 해석·설치해 호환성을 검증한 후 manifest와 배포물 체크섬 참조를 묶는다. 불일치·누락·잠금 변경·체크섬 차이는 manifest 성공으로 기록하지 않고 배포를 보류한다. 실패한 설치의 부분 상태는 후속 시도와 분리하고 기준 잠금 파일은 임의 갱신하지 않는다. 프레임워크 선정안은 G0 공식 호환성 확인 전 확정하지 않는다.
- **책임·의존 계약:** 배포 도구 책임자가 manifest/체크섬을 제공하고 FS-001이 대상 런타임의 출처다. R1의 FS-054가 동일 release 참조를 소비한다.
- **코드동작확인 Test방식:** 깨끗한 시험 환경 설치 재현, 호환되지 않는 확장, 잠금 변경, 체크섬 불일치를 확인한다. 같은 잠금·런타임 입력이면 같은 의존성 집합으로 판정되고 한 요소라도 불일치하면 배포 허용으로 바뀌지 않는지 관찰한다.
- **코드동작확인 로깅방식:** 기술 로그는 manifest/release 참조, 검사 단계, 불일치 종류와 실패 경계를 남긴다. 비밀 저장소 값이나 내부 주소는 남기지 않는다. 설치 관찰과 잠금·체크섬 검증 결과를 증거 참조로 대조한다.
- **완료·반환 증거:** 검증된 런타임 manifest, 잠금 의존성의 재현 결과, 불일치/보류와 남은 호환성 게이트를 반환한다.

<a id="fs-025"></a>
### FS-025 모의·실제 실행환경 분리

- **목적:** 모의 응답과 데이터가 실제 자원 조작·운영 상태로 흘러들지 않게 한다.
- **추가 범위:** 환경별 adapter 조립, 저장소·식별자 namespace 경계, 모드 노출 및 잘못된 조합 거부.
- **수정 범위:** P0 설정 검증과 P3 모의 연동·E1 실제 연동의 선택 경계.
- **삭제 범위:** 실행 중 모드가 모호하거나 모의 식별자가 실제 제어 경로에서 해석되는 동작.
- **goal:** 기동·요청 시 mode, adapter, 데이터 소속을 일관되게 검증하고 사용자/운영자가 실행 모드를 식별하게 한다.
- **non-goal:** 모의 자원에서 실제 서비스로 데이터·VM을 자동 이관하는 것.
- **목표-input:** `deployment_mode`는 실행환경 구분(배포 설정 제공); `adapter_selection`은 허용 외부 구현(구성 제공); `data_namespace`는 DB·작업·VM 소속(저장소 설정 제공); `development_overrides`는 시험 전용 변경 의미(개발 실행자 제공).
- **목표-output:** `mode_validation`은 기동/요청 허용 여부(서비스 수신); `resource_boundary`는 사용할 데이터 경계(adapter/저장소 수신); `visible_mode`는 표시 구분(UI·로그 수신).
- **구현 동작:** 적용은 P0에서 조합 검증, P3에서 모의 adapter, E1에서 실제 adapter다. 기동 전에 모드·adapter·DB namespace·자격증명 참조가 허용 조합인지 검사하고 잘못된 조합은 실패 폐쇄한다. 요청 시 VM/작업 namespace를 확인한 후에만 adapter에 전달한다. 모의 데이터는 모의 저장소와 별도 ID 경계에 유지하며 실제 자격 증명으로 변환하지 않는다. 실행 mode와 adapter 선택은 결과·화면·로그에 이어진다. 불일치나 모드 확인 실패 시 외부 호출 전에 중단하고 재시도는 올바른 배포 설정에서만 한다.
- **책임·의존 계약:** Integrations/설정 경계가 조립과 namespace 검사를 소유한다. FS-021~024 모의 동작과 FS-028 실제 adapter는 각자 허용 인터페이스를 제공한다. 비밀 참조는 런타임에 승인된 저장소가 공급하며 실제 값은 기록하지 않는다.
- **코드동작확인 Test방식:** 실제 mode에 모의 adapter/강제 override, 모의 ID의 실 adapter 전달, 잘못된 저장소 선택을 시험한다. 차단 시 외부 요청이 발생하지 않고 사용자에게 모드가 명확하며 모의 VM이 실제 SSH 가능 정보로 표시되지 않는지 관찰한다.
- **코드동작확인 로깅방식:** 기술 사건에 mode·adapter 분류·namespace 검사·차단 이유·외부 호출 여부를 남기고 경계 위반 시 보안 감사 사건을 연결한다. 자격 증명·주소·본문은 제외하고, Test의 외부 호출 관찰과 함께 대조한다.
- **완료·반환 증거:** 허용 조합표의 근거, 잘못된 조합의 차단, namespace 분리와 사용자 표시 확인, 실제 전환에 남은 G1 조건을 반환한다.

<a id="fs-026"></a>
### FS-026 감사 원장 기록·확인

- **목적:** 중요 행위와 업무 변경의 책임·결정·결과를 추적 가능한 원장으로 남긴다.
- **추가 범위:** 업무 변경과 연계된 감사 삽입, 권한 제한된 이력 조회, 원장 무결성 점검.
- **수정 범위:** 감사 대상 작업은 업무 변경과 같은 트랜잭션 경계를 사용하며 거부 사건은 변경 없이 감사된다.
- **삭제 범위:** 기술 로그만으로 감사 완료를 간주하거나 앱 계정이 원장을 갱신·삭제하는 동작.
- **goal:** 업무 변경과 감사 사건이 함께 반영되거나 함께 실패하며, 감사 원장 보존 실패가 명시적으로 드러난다.
- **non-goal:** 일반 앱 권한으로 purge, 감사 원장을 기술 로그로 대체하는 것.
- **목표-input:** `actor`는 행위 사용자/서비스/운영자(인증·운영 경계 제공); `target`은 대상 참조(업무 모듈 제공); `action`은 행위 의미(업무 모듈 제공); `decision`은 허용/거부·변경 결과(정책 제공); `transaction_context`는 업무 반영 관계(저장소 제공).
- **목표-output:** `audit_ref`는 보존 사건 식별(업무 호출자 수신); `audit_history`는 권한 있는 이력(관리 조회자 수신); `integrity_result`는 업무/감사 일치 판정(검증 담당 수신).
- **구현 동작:** 공통 Audit append·정제·권한 기반은 P1의 초기 계정/인증 감사 전에 준비하고, P2에서 Vm/Jobs 업무 트랜잭션·이력 조회로 통합한다. 허용 업무 변경과 Audit 삽입은 호출자의 같은 트랜잭션에서 성공/롤백하며 감사 제공자가 별도 커밋하지 않는다. 거부는 업무 무변경 감사로 남긴다. 앱 원장은 추가/조회만 허용한다. 감사 저장 실패는 성공으로 숨기지 않고 접수 제한/진단 신호를 반환한다. purge·archive·상시 경보의 전체 구현은 R2에 이어 붙이며 초기 Audit 실행의 선행으로 요구하지 않는다.
- **책임·의존 계약:** Audit가 사건 의미·append/조회·정제 정책을, 업무 호출자가 트랜잭션을 소유한다. 실행 선행은 FS-057의 해당 schema·권한 준비다. R2의 FS-048 정리는 이후 관리 소비자이며 P1/P2 실행 선행이 아니다.
- **코드동작확인 Test방식:** 허용·거부·중복·업무 실패·감사 삽입 실패·동시 변경을 확인한다. 업무 변경 성공에는 대응 감사가 정확히 하나 연결되고 감사 실패에는 업무 변경이 남지 않는 원자성, 앱 권한의 update/delete 거부, purge 권한 분리를 관찰한다.
- **코드동작확인 로깅방식:** 원장에 행위자·대상 참조·작업·결정·변경 의미·UTC 시각을 보존한다. 기술 로그에는 삽입 장애 분류와 추적 참조만 남긴다. 원장·업무 행·권한 검사 결과를 대조하며 원장 값 전체를 기술 로그에 복제하지 않는다.
- **완료·반환 증거:** 원자성 결과, 앱/관리 권한 검사, 실패·용량 경보 처리와 업무 행 대조 근거를 반환한다. 감사 실패가 은폐되지 않았는지 명시한다.

<a id="fs-027"></a>
### FS-027 기술 로그·추적·민감정보 제거

- **목적:** 서비스·요청·작업 사건을 연결하면서 비밀과 불필요한 원문 노출을 막는다.
- **추가 범위:** 구조화 기술 로그, 추적 상관 관계, 비밀 제외·마스킹 정책, 기록 실패 감지.
- **수정 범위:** API·worker·모의 앱·운영 절차는 공통 추적 의미와 오류 분류를 사용한다.
- **삭제 범위:** 전체 요청/응답 본문, 인증 값, 개인키, 내부 접속 주소의 로그 기록과 조용한 기록 실패.
- **goal:** 오류·상태 전이를 사건 단위로 확인하고 로그 저장 실패·공간 부족을 운영자가 탐지한다.
- **non-goal:** 감사 원장·Test 증거를 기술 로그에 혼합하거나 모든 데이터를 덤프하는 것.
- **목표-input:** `event_context`는 서비스·mode·release·요청/작업 추적·시도·사건·오류·소요 의미(호출 경계 제공); `logging_policy`는 수준·제외/마스킹·출력 경계(운영 설정 제공).
- **목표-output:** `structured_record`는 정책에 맞는 기술 사건(운영자 수신); `correlation`은 연결 가능한 식별 관계(진단자 수신); `logging_failure_signal`은 기록 장애 관찰(감시 담당 수신).
- **구현 동작:** 적용은 P0 공통 기반을 정하고 P1~P4에서 흐름별 적용, R 단계에서 회전·감시와 결합한다. 수신 경계에서 추적 식별을 생성/검증하고 각 서비스·release·mode·사건·시도·결과·소요·오류 분류를 구조화한다. 감사 대상은 FS-026 원장으로 전달하고 기술 로그에는 참조만 남긴다. 기록 전에 비밀번호·세션/CSRF 원문·토큰·인증서 개인키·전체 본문·내부 주소를 제거한다. 기록 backend 실패나 공간 임계 도달은 독립 감시 신호와 운영 문제로 만들며 작업/감사 성공을 조작하지 않는다. 단순 파일 출력의 일부 성공과 회전 후 재열기 실패도 장애로 취급한다.
- **책임·의존 계약:** Logging 경계는 형식·마스킹·실패 신호를 소유하고 호출 모듈은 유의미한 사건과 추적 값을 제공한다. FS-048 회전/보존 및 FS-049 감시가 오류를 소비한다.
- **코드동작확인 Test방식:** 정상 인증·VM·통지 흐름의 상관 관계, 민감 시험 값 주입 후 노출 부재, 장기 쓰기·회전·권한 실패를 확인한다. 로그 장애가 표시되고 감사/청구 유실이 성공으로 보고되지 않는 불변식을 관찰한다.
- **코드동작확인 로깅방식:** 기술 로그에는 사건·상관 식별·서비스/mode/release·오류 분류·소요 의미만 기록한다. 감사와 Test 증거는 별도 저장한다. 비밀 검색 결과, 추적 연결, 파일/backend 오류를 정제 검증 보고서 및 업무 상태와 대조한다.
- **완료·반환 증거:** 필드/제외 정책, 흐름별 추적 확인, 민감정보 검색 결과, 저장·회전 실패 감지 근거를 반환한다.

<a id="fs-039"></a>
### FS-039 Windows 인프라 상태·검증 기록

- **목적:** 관리자가 Windows 호스트·VM의 실습 상태와 검증 이력 및 그 한계를 확인한다.
- **추가 범위:** 등록된 대상 참조별 관찰값·신선도·오류와 실행/검증 증거의 관리 화면 의미.
- **수정 범위:** 관리자 인프라 조회는 등록된 관찰 계약만 사용하며 고객용 VM 상태와 별도 권한을 적용한다.
- **삭제 범위:** 모의값·오래된 관찰을 실제 현재 상태 또는 지원성 증명으로 표시하는 것.
- **goal:** 관찰 시점, 성공/실패/미실행, 근거, 확인하지 않은 장애 범위를 관리자에게 구분해 제공한다.
- **non-goal:** 웹에서 새 인프라 자동구축·자동복원 서비스 추가.
- **목표-input:** `admin_context`는 조회 권한(Identity 제공); `infra_refs`는 등록 호스트/노드/VM 참조(운영 목록 제공); `observations`는 정제 상태·시각·장애 정보(허용 관찰자 제공); `verification_records`는 조건·증거·한계(실습 담당 제공).
- **목표-output:** `infrastructure_view`는 역할·상태·마지막 관찰·문제(관리자 수신); `verification_history`는 결과와 근거(관리자 수신); `scope_limitations`는 실제 시험 범위(운영자 수신).
- **구현 동작:** 적용은 E0 증거 구조를 정하고 E4 관리자 표시로 연결한다. 관리자 권한 확인 후 등록된 참조만 조회하고 관찰 출처·시각·mode·오류·신선도와 검증 기록을 결합한다. 오래된 값은 현재값과 구별하고 미실행/조건 대기를 성공으로 변환하지 않는다. Windows 실습의 Hyper-V 호스트와 중첩 Compute의 관리 경계를 별도로 표시한다. 관찰 소스가 실패하면 마지막 관찰 시각과 실패를 노출하고 신규 결과를 생성하지 않는다.
- **책임·의존 계약:** Infrastructure 관찰 adapter는 Windows 관리 경계의 정제 결과를 제공하고 관리자 콘솔은 권한·표시를 담당한다. 실제 VMM 조작은 별도 Windows 저장소 소유다. FS-040의 단계 증거와 연결한다.
- **코드동작확인 Test방식:** 정상·장애·오래된 관찰·증거 없음·회원 접근을 확인한다. 화면의 시각·모드·결과가 원천 관찰과 맞고 미확인 지원성/동작 성공을 주장하지 않는지 확인한다.
- **코드동작확인 로깅방식:** 기술 로그에 수집/조회 사건·대상 참조·관찰 시각·신선도·오류 분류를 남긴다. 검증 결과는 별도 Test 증거다. 정제 호스트 관찰과 UI 표시를 대조하고 내부 주소·자격증명은 제외한다.
- **완료·반환 증거:** 권한별 표시 결과, 실제 관찰과 화면 대조, 오래됨/미실행 표현 및 검증 범위의 한계를 반환한다.

<a id="fs-040"></a>
### FS-040 인프라·Linux 별도 검증·보존 축소

- **목적:** 인프라와 Linux 구성을 별도 검증하고 고객 VM·디스크를 보존하며 최소 서비스 구성으로 전환한다.
- **추가 범위:** 단계별 자원·검증 증거, 인프라 8→4 및 Linux 8→4 전환 목록, 보존 대조와 가동 상태 기록.
- **수정 범위:** 승인된 토폴로지·실측 자원·선정 기술이 확보된 후에만 실습 절차를 구체화한다.
- **삭제 범위:** 두 8대 검증을 동시에 수행하거나 고객 VM/디스크를 보존 확인 없이 제거하는 절차.
- **goal:** 두 검증이 분리되고 각 축소 전후 고객 데이터·서비스 역할·자동 시작 제한을 증거로 확인한다.
- **non-goal:** 미정 자원·제품 라이선스·복제/전환 기술을 확정된 것으로 가정하는 것.
- **목표-input:** `approved_topology`는 승인 역할·대수·계층(운영 결정 제공); `resource_evidence`는 자원·권한·지원성(게이트 담당 제공); `test_plan`은 단계 순서·합격 의미(검증 책임자 제공); `preservation_plan`은 전환·복구 관계(운영 책임자 제공).
- **목표-output:** `stage_evidence`는 각 단계의 별도 결과(게이트 수신); `preserved_resources`는 전후 VM·디스크 동일성 참조(복구 담당 수신); `active_topology`는 축소 후 가동/자동 시작 상태(운영자 수신); `blockers`는 불충족 조건(책임자 수신).
- **구현 동작:** G1 확인 뒤 E0에서 실행한다. 인프라 대규모 검증과 Linux 대규모 검증의 선후는 실제 자원·사용자 결정으로 정하며 순서를 미리 고정하지 않는다. 두 검증은 동시에 가동하지 않고 각 검증/축소의 별도 증거를 남긴다. Linux 서비스 VM은 물리 Hyper-V, 고객 VM은 중첩 Compute/VMM 경계로 구별한다. 보존 전환 전에 VM·디스크 연결·완전성·읽기/복구 가능성을 확인하고 진행 중 변경을 정리한다. 검증과 보존이 확인된 구성만 최소 역할로 줄이고 추가 VM 자동 시작을 제한한다. 불일치·불완전 백업·자원 미확인은 전환을 중단한다. 단일 물리 호스트의 실습을 물리 장애 내성으로 표현하지 않는다.
- **책임·의존 계약:** 실습 담당이 단계·보존 증거를 소유한다. G1·Windows 관리 경계·전환에 필요한 기본 백업/복구 가능성 확인이 실행 선행이다. FS-052/053의 기본 절차에서 필요한 부분을 전환 전에 검증하되 R2의 반복 운영·복구 목표 합격 전체를 E0 선행으로 요구하지 않는다. 정족수·복제 방식은 사용자 결정 전 제안으로 유지한다.
- **코드동작확인 Test방식:** 순서 강제, 두 실습의 동시 진행 방지, 보존 전후 참조 일치, 디스크 누락·자동시작 위반·호스트 재부팅을 관찰한다. 축소는 해당 구간의 모든 자원/보존 조건이 충족될 때만 기록되는지 확인하고 단일 물리호스트를 HA로 표시하지 않는지 확인한다.
- **코드동작확인 로깅방식:** 검증 기록에 단계·선정 기술·자원 근거·전후 자원 참조·시각·결과·한계를 남긴다. 기술 로그는 작업 추적과 오류 분류만 기록한다. 실제 VM/디스크 관찰 및 백업/복구 증거를 연결하고 주소·비밀은 제외한다.
- **완료·반환 증거:** 인프라 시험과 Linux 시험의 분리된 보고, 축소 전후 보존 대조, 고객 VM/디스크 복구 가능성, 축소 후 역할·자동시작 상태 및 미해결 게이트를 반환한다.

### FS-041 Linux·DB·접근 경로 상태 관찰

- **목적:** Linux 서비스 경로와 DB 상태를 관찰하되 서비스 MySQL과 별도 Galera 시험 구성을 분리한다.
- **추가 범위:** 허용 출처에서 읽은 노드·서비스·정족수·경로 관찰, 시각과 신선도·실패 표현.
- **수정 범위:** E0 관찰 모델을 E4 관리자 인프라 상태와 연결한다.
- **삭제 범위:** Galera 상태를 서비스 DB의 복제/장애조치 합격으로 간주하는 것.
- **goal:** 실제 관찰된 상태와 관찰 실패를 구분하고 선정된 정족수 조건과 비교한다.
- **non-goal:** 상태 관찰 경로에서 임의 Linux 명령 실행이나 DB 토폴로지 자동 변경.
- **목표-input:** `infra_inventory`는 등록 노드·서비스·역할(운영자 제공); `observation_sources`는 허용된 조회 경계(인프라 담당 제공); `quorum_definition`은 승인된 정족수 조건(결정 기록 제공); `admin_context`는 조회 권한(Identity 제공).
- **목표-output:** `linux_observations`는 노드·DB·정족수·Nginx/Keepalived 경로·시각(관리자 수신); `freshness_and_errors`는 오래됨/실패(관리자 수신); `service_separation`은 서비스 MySQL과 Galera 구분(운영자 수신).
- **구현 동작:** 적용은 E0에서 관찰 출처·역할을 선정하고 E4에서 관리자 조회로 노출한다. 권한과 등록 대상을 확인한 뒤 읽기 전용 관찰을 수행하고 대상 역할·source·시각·결과 신선도를 함께 저장한다. 서비스 MySQL과 Galera는 다른 시스템 식별로 취급하고 집계/판정도 분리한다. 정족수 정의가 승인되지 않았으면 정족수 결과를 미정으로 두며 건강 판정에 합격 처리하지 않는다. 관찰 timeout/접속 실패는 마지막 관찰을 덮지 않고 실패를 병기한다.
- **책임·의존 계약:** Infrastructure 관찰자·인벤토리가 원천, Linux 관리자 화면이 소비자다. 정족수·VIP 세부는 해당 실습 전에 정한다. Windows 표시인 FS-039를 Linux 관찰의 필수 제공자로 요구하지 않으며 정제/신선도 표시 규칙만 공유한다.
- **코드동작확인 Test방식:** 노드/서비스 중지, 관찰 실패, VIP 전환, 정족수 상실을 실환경에서 대조한다. 관찰 출처가 잘못되거나 Galera만 정상인 경우 서비스 MySQL의 성공으로 표현되지 않는지 확인한다.
- **코드동작확인 로깅방식:** 기술 로그에 역할·대상 참조·관찰 종류·시각·상태 변화·오류 분류를 남긴다. 정제된 실제 서비스 증거에 연결하고 내부 주소·인증정보는 제거한다.
- **완료·반환 증거:** 관찰 출처와 권한, 신선도·실패 처리, Galera/서비스 MySQL 분리 대조, 정족수 선정 또는 미정 상태를 반환한다.

<a id="fs-042"></a>
### FS-042 허용 Linux 제어·장애 복구 확인

- **목적:** 선정된 제한 작업만 권한 있는 운영자가 실행하고 데이터·경로 복구 결과를 확인한다.
- **추가 범위:** 작업 allowlist, 등록 대상 확인, 승인된 executor 경계, 작업 이력 및 복구 관찰.
- **수정 범위:** E4 제어 절차는 E0에서 검증된 Linux 배치와 FS-041 관찰 결과에 의존한다.
- **삭제 범위:** 웹에 범용 셸·임의 명령·자유 형식 대상 입력을 노출하는 것.
- **goal:** 각 제어 작업이 허용 동작·대상·권한·제한 인자와 연결되고 중단/재합류/경로 복구 후 일관성이 확인된다.
- **non-goal:** executor 기술을 사전 확정하거나 새 웹 자동복원 서비스를 만드는 것.
- **목표-input:** `admin_context`는 실행 권한(Identity 제공); `target_ref`는 등록 대상(인벤토리 제공); `allowed_operation`은 선정 executor의 허용 동작(운영 정책 제공); `validated_parameters`는 제한 인자(업무 정책 제공); `recovery_policy`는 실패·재합류 조건(검증 계획 제공).
- **목표-output:** `control_job`은 추적 가능한 실행(운영자 수신); `verified_control_result`는 변경/복구와 관찰 시각(검증자 수신); `consistency_evidence`는 데이터·경로 대조(운영자 수신); `failure_or_remaining`은 남은 문제(운영자 수신).
- **구현 동작:** E4에서 executor·정족수·허용 작업/복구 정책을 선정한 뒤 적용한다. 관리자·대상·allowlist·인자를 검증하고 승인 계약에 맞춰 작업을 기록한다. 한 요청의 동작 단위·동일 제출 식별·멱등 재실행 지원은 선정 executor와 인프라 Jobs 계약에서 정할 설계안이며 현재 확정 정책으로 간주하지 않는다. 불명확 결과를 자동 재실행하지 않고 사후 읽기 관찰로 재합류·데이터 일관성·경로를 확인한다. 실패/부분 적용은 재확인으로 남긴다. 동시 수정/삭제 시험은 정한 시험창·격리 조건을 충족해야 한다.
- **책임·의존 계약:** Infrastructure가 허용 작업 정책, executor가 제한 실행을 소유한다. 기술·서비스 권한은 미정이며 E4 실행은 FS-041 관찰·FS-026 감사·FS-027 기술 로그를 선행으로 한다. R2의 FS-049 감시는 이후 소비자이며 E4 착수의 선행 조건으로 요구하지 않는다.
- **코드동작확인 Test방식:** 비관리자·미등록 대상·임의 명령·허용 외 인자 거부, 노드 중지/재합류, 네트워크 분리/경로 전환과 데이터 대조를 확인한다. 거부 입력이 executor로 전달되지 않고 작업 성공은 사후 관찰까지 끝나야 판정되는지 확인한다.
- **코드동작확인 로깅방식:** 감사 원장에 관리자·대상 참조·허용 연산 분류·결정·작업 결과를 남긴다. 기술 로그에는 추적·단계·오류만 기록한다. 검증 증거에 일관성·재합류·경로 관찰을 연결하고 명령 전문·비밀·데이터 원문을 제외한다.
- **완료·반환 증거:** 선정 executor와 권한 경계, 허용/거부 결과, 부분 실패 처리, 데이터 일관성과 경로 복구의 실제 관찰 증거를 반환한다.

<a id="fs-043"></a>
### FS-043 VPC 분리·연결·제어

- **목적:** 선정 기술로 시험 네트워크 분리·연결 정책과 실패 복구를 검증한다.
- **추가 범위:** 등록된 시험 네트워크 참조, 정책 적용 작업, 양측 통신 관찰 및 복구 결과.
- **수정 범위:** E4 실습은 G1에서 확인된 네트워크·VMM 경계와 구현 결정을 사용한다.
- **삭제 범위:** 미정 VPC 기술을 구현/운영 완료로 표시하거나 검증 전 정책을 운영 적용하는 것.
- **goal:** 허용·차단 관계를 양방향에서 실제 확인하고 부분 적용 시 상태를 추적해 복구한다.
- **non-goal:** 외부 네트워크에 대한 임의 연결, 일반 고객용 네트워크 제어 기능 확장.
- **목표-input:** `vpc_refs`는 등록 시험 네트워크(운영 인벤토리 제공); `connectivity_policy`는 허용/차단 관계(승인 정책 제공); `requested_transition`은 분리/연결 의미(관리자 요청 제공); `admin_context`는 권한(Identity 제공); `implementation_choice`는 선정 제어 기술(결정 기록 제공).
- **목표-output:** `vpc_job`은 변경 이력(운영자 수신); `observed_connectivity`는 양측 통신 결과·시각(검증자 수신); `applied_policy`는 관찰된 규칙 상태(운영자 수신); `recovery_result`는 복구 결과(운영자 수신).
- **구현 동작:** 적용은 E4이며 G1 네트워크 확인과 기술 선택 전에는 실행할 수 없다. 대상 참조·관리 권한·정책 버전을 검증하고 승인된 전환만 작업화한다. 정책 적용은 단계별 결과를 추적하며 중간 실패 시 성공으로 합성하지 않고 현재 상태를 재관찰한다. 분리/연결 후 양측에서 허용·차단 시험을 수행하고 정책과 실제 도달성을 대조한다. 되돌리기는 미리 승인된 복구 전이만 수행하며 제어 채널 상실 시 자동으로 광범위한 연결을 열지 않는다.
- **책임·의존 계약:** Infrastructure가 요청·허용 관계, 사용자 선정 별도 네트워크 executor가 제한 실행을 소유한다. VMM Gateway에 Linux/VPC 제어를 결합하지 않는다. E4 실행 선행은 해당 기술/네트워크 결정·FS-026 감사·FS-027 기술 로그·통신 관찰이며, FS-049 상시 경보는 R2 후속 소비자다.
- **코드동작확인 Test방식:** 분리 차단·연결 허용·정책 밖 차단·무권한 거부·부분 적용·복구를 양쪽 네트워크에서 확인한다. 기술 미정이면 실행 Test는 조건 대기로 두며, 어느 한쪽 관찰만으로 정책 성공을 판정하지 않는다.
- **코드동작확인 로깅방식:** 감사에는 네트워크 참조·정책 버전·행위·결정·작업 결과를 남긴다. 기술 로그는 작업 단계·오류 추적만 기록한다. 정제 통신 증거를 양쪽 관찰과 연결하고 내부 주소·전체 방화벽 규칙을 공개하지 않는다.
- **완료·반환 증거:** 선정 기술의 결정 근거, 정책 적용 전후, 양방향 허용/차단 증거, 부분 실패 복구 결과와 잔여 위험을 반환한다.

<a id="fs-048"></a>
### FS-048 로그 회전·보존·원장 정리

- **목적:** 저장 용량을 관리하면서 기술 로그와 업무 원장의 보존·정리 권한을 지킨다.
- **추가 범위:** 로그 회전·압축·재열기·권한 확인, 원장 archive와 별도 purge 절차, 용량 경보.
- **수정 범위:** 보존·용량·기간 정책은 실측과 운영 결정 후 적용하며 기존 제안 수치를 확정으로 간주하지 않는다.
- **삭제 범위:** 활성/재확인 작업이나 감사·청구 원장을 일반 로그 정리와 함께 삭제하는 것.
- **goal:** 기술 로그 저장이 계속되고 원장 정리는 추적·권한·archive 뒤 별도로 수행되며 공간 부족이 가시화된다.
- **non-goal:** 앱 서비스가 자체 감사/청구 purge를 수행하는 것.
- **목표-input:** `retention_policy`는 기록별 보존·회전·용량 의미(운영 결정 제공); `record_inventory`는 크기·시각·활성 관계(저장소 관찰 제공); `cleanup_authority`는 전용 정리 권한(관리자 제공).
- **목표-output:** `rotation_archive_result`는 회전·압축·재열기·archive 결과(운영자 수신); `cleanup_report`는 처리/보호 대상과 이유(감사자 수신); `capacity_signal`은 공간 부족·접수 제한 필요성(감시 담당 수신).
- **구현 동작:** 적용은 R2다. 승인된 정책·권한을 확인하고 기술 로그 회전을 별도 수행한다. 회전 후 writer가 새 대상에 기록하는지와 서비스 계정 권한을 검사한다. 원장 정리는 별도 관리자가 보존 대상·활성 작업·재확인 여부를 분류하고 사전 archive·무결성 확인을 마친 후에만 실행한다. 앱 DB 계정에는 purge 권한을 주지 않는다. archive/회전 실패나 공간 부족 시 삭제로 숨기지 않고 경보하고, 원장 저장 여유가 부족하면 감사/청구 기록을 잃지 않도록 신규 업무 접수를 제한한다. 기간·용량 기준이 미정이면 삭제하지 않고 결정 대기로 둔다.
- **책임·의존 계약:** 운영자가 보존 정책과 전용 정리 승인을 소유한다. Logging/DB 역할은 재열기·권한·대상 목록을 제공한다. FS-026 원장 권한과 FS-049 용량 경보에 의존한다.
- **코드동작확인 Test방식:** 시간/크기 경계, 회전 후 지속 기록, 서비스 권한, archive 실패, 활성·재확인 작업 보호, 감사/청구 원장 보호를 확인한다. 부족 용량이 경보·접수 제한으로 나타나며 원장이 조용히 사라지지 않는지 관찰한다.
- **코드동작확인 로깅방식:** 운영 사건에 정책 참조·대상 종류·처리 결과·오류·보호 이유·공간 신호를 기록한다. 정리 전후 인벤토리·archive 검증·원장 수와 경보를 대조하며 원문 로그나 고객 데이터를 증거에 복사하지 않는다.
- **완료·반환 증거:** 승인 정책 버전, 회전 후 쓰기, archive·purge 권한 분리, 보호 대상과 용량 부족 대응의 실제 기록을 반환한다.

<a id="fs-049"></a>
### FS-049 서비스·작업 감시·경보

- **목적:** 서비스·작업·저장소·백업·인증서 이상을 탐지하고 경보 및 해제 이력을 남긴다.
- **추가 범위:** 관찰 항목, 판정·중복 억제 정책, 경보 상태와 허용 통지 경로 참조.
- **수정 범위:** Prototype은 화면·기술 로그 관찰, Production은 E4에서 확정된 알림 연계를 사용한다.
- **삭제 범위:** 미실행·관찰자 장애를 정상으로 표시하거나 반복 장애를 무한 발송하는 것.
- **goal:** 장애 발생·탐지·통지 시도·복구 해제를 연결해 운영자가 대응 상태를 판단한다.
- **non-goal:** 통지 경로 자체가 모든 감시를 보장한다고 간주하거나 미확정 목표값을 확정하는 것.
- **목표-input:** `health_observations`는 서비스/worker·대기·오류·디스크·백업·인증서 관찰(각 운영 소스 제공); `alert_policy`는 판정·중복 억제·해제 의미(운영자 결정 제공); `destination_refs`는 허용 경로(알림 설정 제공).
- **목표-output:** `health_assessment`는 판정과 근거(운영자 수신); `alert_state`는 발송/억제/해제 상태(통지 adapter 수신); `operational_issue_ref`는 추적 문제(당직자 수신).
- **구현 동작:** 적용은 R2이며 알림 연결은 E4 경로 준비 뒤다. 각 관찰을 출처·시각·신선도와 수집하고, 승인된 정책으로 문제를 판정한다. 동일 미해결 사건은 억제 키로 묶어 중복을 줄이고, 해결은 회복 관찰이 확인된 후 해제한다. 관찰기·로그 저장소·알림 경로 자체의 실패도 별도 문제로 표시한다. 디스크 부족/감사·청구 저장 실패는 정상 통지 여부와 별개로 접수 차단 필요성을 유지한다. 미정 기준은 측정 결과로 확정하지 않는다.
- **책임·의존 계약:** 감시 책임자는 관찰 정책과 이슈 생명주기를 소유한다. worker·DB·디스크·백업·인증서 출처가 관찰을 공급하고 FS-044~045 허용 통지 경로를 제공한다. Prototype 외부 발송은 추가하지 않는다.
- **코드동작확인 Test방식:** worker 종료·callback 누락·DB 실패·공간 부족·백업/인증서 기준 초과 및 감시 소스 실패를 주입한다. 탐지, 경보 중복 억제, 복구 관찰 뒤에만 해제, 통지 경로 실패의 가시성을 확인한다.
- **코드동작확인 로깅방식:** 기술 로그에 관찰 종류·시각·정책 참조·상태 변화·발송 시도·실패 분류를 기록한다. 감사가 필요한 운영 행위는 원장에 둔다. 탐지/통지/해제 사건을 FS-044~045 결과와 실제 소스 관찰에 대조한다.
- **완료·반환 증거:** 관찰 출처·판정 정책·중복/해제 동작·감시 자체 장애 처리·통지 시험 결과를 반환한다.

<a id="fs-050"></a>
### FS-050 인증서 갱신·비밀정보 권한 관리

- **목적:** 서비스 간 신뢰와 런타임 비밀 접근을 제한하고 교체 후 연결을 검증한다.
- **추가 범위:** 서비스 신원 관계, 신뢰·갱신 절차, 서비스 계정별 비밀 접근 검증.
- **수정 범위:** R1·R2 비밀 공급은 배포 시 안전한 참조로 연결하며 코드·로그에 비밀 값을 복사하지 않는다.
- **삭제 범위:** 개인키·토큰을 저장소/웹 루트에 보관하거나 공용 계정으로 비밀을 공유하는 것.
- **goal:** 갱신·폐기·권한 회수 후 승인된 서비스만 정상 통신하고 실패가 명확히 관찰된다.
- **non-goal:** 미확정 CA/신뢰 기술을 선택하거나 기존 키를 검증 없이 재사용하는 것.
- **목표-input:** `service_identity_map`은 서비스와 인증서/권한 관계(운영 인벤토리 제공); `trust_policy`는 신뢰·출발지 의미(보안 결정 제공); `renewal_policy`는 갱신/폐기·CA 운영(승인 절차 제공); `secret_access_policy`는 서비스별 읽기 범위(비밀 저장 관리자 제공).
- **목표-output:** `trust_validation`은 신원·체인·용도·통신 판정(운영자 수신); `rotation_result`는 교체와 재확인(운영자 수신); `access_validation`은 권한별 허용/거부(보안 담당 수신).
- **구현 동작:** 적용은 R1에서 배포 접근을 준비하고 R2에서 갱신·권한 운영을 검증한다. 서비스 신원과 비밀 참조를 등록하고 대상 프로세스/계정의 최소 읽기 권한을 확인한다. 신규 인증서/비밀 참조를 배포·검증한 뒤 연결을 재확인하고, 성공 전 기존 유효 경로를 폐기하지 않는다. 실패하면 교체 완료로 표시하지 않고 승인된 복구 절차와 만료 위험을 경보한다. 인증서 폐기·CA 운용·기존 키 재사용은 보안 적합성과 결정 근거 확인 전 보류한다.
- **책임·의존 계약:** 보안/운영 담당이 신뢰·권한을 소유하고 배포 도구는 비밀 참조만 전달한다. G1 실제 통신의 신원/비밀 기반을 먼저 확인하고 R1 배포와 R2 교체 운영을 검증한다. FS-049는 R2 만료 경보 소비자이며 R1 최소 권한·신뢰 확인을 막는 선행이 아니다.
- **코드동작확인 Test방식:** 만료/잘못된 체인·다른 서비스 인증서·미등록 출발지·비인가 계정 읽기·갱신 후 요청/통지를 시험한다. 허용되지 않은 계정은 비밀을 읽지 못하고 교체 실패 시 기존 신뢰 상태가 성공으로 기록되지 않는지 확인한다.
- **코드동작확인 로깅방식:** 보안 감사에는 정제된 인증서 참조·서비스 역할·검사·교체·권한 결과를 남긴다. 기술 로그는 연결 오류 분류만 포함한다. 개인키·비밀 파일·내부 주소 없이 교체 전후 실제 연결 증거를 대조한다.
- **완료·반환 증거:** 신뢰/계정 권한 검사, 갱신 후 통신, 실패·복구 절차와 미정 CA·출발지 결정사항을 반환한다.

<a id="fs-051"></a>
### FS-051 재부팅 후 서비스 기동·가동 대수

- **목적:** 의존성이 준비된 순서로 최소 역할 서비스를 기동하고 추가 VM 자동 시작을 제한한다.
- **추가 범위:** 재부팅 후 역할별 준비 확인, 가동 인벤토리, 의존 실패 기록.
- **수정 범위:** 시작 관계는 실제 선정 토폴로지와 FS-040 축소 결과에 맞춘다.
- **삭제 범위:** 준비 확인 없이 고객 작업을 허용하거나 모든 VM을 무차별 자동 시작하는 것.
- **goal:** 재부팅 후 각 역할이 실제 준비됐는지 확인하고 실패 의존성을 노출한다.
- **non-goal:** 한 물리호스트·상시 4+4 배치를 HA 보장으로 표현하는 것.
- **목표-input:** `service_topology`는 승인 최소 역할(운영 인벤토리 제공); `startup_dependencies`는 AD/DNS·저장·Compute 및 Linux DB/API/콘솔 준비 관계(구성 제공); `autostart_policy`는 추가 VM 제한(운영 결정 제공); `host_restart`는 재부팅 사건(호스트 관찰 제공).
- **목표-output:** `startup_assessment`는 역할별 기동/준비 판정(운영자 수신); `active_inventory`는 실제 가동/종료 역할(운영자 수신); `dependency_errors`는 준비 실패·자동 시작 위반(운영자 수신).
- **구현 동작:** 적용은 R1이다. 승인된 최소 토폴로지와 의존 순서를 확인하고 재부팅 전 추가 VM의 자동 시작 정책을 적용한다. 재부팅 후 AD/DNS·저장·관리·Compute, 이어 Linux DB/API/콘솔 등 선정 순서에 따라 준비 신호를 관찰한다. 준비가 안 된 역할은 기동 완료로 기록하지 않고 작업 접수를 보류한다. 고객 VM은 승인된 절차에 따라 별도 시작하며 역할·가동 수를 실측해 대조한다. 의존 실패 시 무한 재시작이나 추가 VM 자동 기동으로 확장하지 않고 중단 사유를 기록한다.
- **책임·의존 계약:** 운영자가 기동 절차·인벤토리를 소유한다. 실행 선행은 FS-040 최소 구성·FS-041 및 서비스별 준비 관찰이다. R1은 직접 readiness 확인으로 검증하고 FS-049 자동 감시는 R2에 연결한다. 단일 호스트 장애는 백업·복구 범위로 유지한다.
- **코드동작확인 Test방식:** 실제 호스트 재부팅, 의존 서비스 지연/실패, 추가 VM 자동시작 제한과 역할별 준비 상태를 확인한다. 준비 전 고객 작업이 수락되지 않고 가동 목록이 관찰 결과와 일치하는지 확인한다.
- **코드동작확인 로깅방식:** 운영 기록에 재부팅 사건·역할별 기동/준비 시각·상태·실패를 남긴다. 기술 로그의 서비스 health와 호스트 인벤토리를 대조하며 내부 주소·비밀은 제외한다.
- **완료·반환 증거:** 재부팅 조건·의존 순서·실제 가동 역할 수·고객 작업 접수 게이트·실패 처리 근거를 반환한다.

<a id="fs-052"></a>
### FS-052 DB·설정·고객 VM 백업

- **목적:** 복구에 함께 필요한 업무 DB·설정·고객 VM/디스크를 일관된 집합으로 보존한다.
- **추가 범위:** 백업 범위 관계, DB·디스크 일관성 절차, 별도 매체 기록, 완전성 검증.
- **수정 범위:** 미디어·일정·보존·목표는 G2에서 자원/정책 확인 후 확정한다. 현재 제안 목표를 사실로 취급하지 않는다.
- **삭제 범위:** DB와 고객 디스크의 관계를 확인하지 않은 채 각기 성공한 산출물을 하나의 복구 가능 집합으로 표시하는 것.
- **goal:** 하나의 백업 집합이 구성원·시점·무결성·복구 관계를 증명한다.
- **non-goal:** 새 웹 자동백업/복원 서비스를 추가하거나 복원 시험 없이 복구 가능성을 선언하는 것.
- **목표-input:** `backup_scope`는 업무 DB·필수 설정·고객 VM/디스크 관계(운영자 제공); `consistency_policy`는 정합성 확보 순서(결정된 절차 제공); `destination_ref`는 승인된 별도 매체 참조(관리자 제공); `backup_policy`는 주기·보존·권한 의미(운영 결정 제공).
- **목표-output:** `backup_set_ref`는 연결된 집합 식별(복구 담당 수신); `integrity_evidence`는 완전성·정합성 검사(검증자 수신); `backup_result`는 성공/중단/실패와 시각(감시·운영자 수신).
- **구현 동작:** 적용은 E 기본 수단으로 데이터 관계를 정하고 R2에서 반복 검증한다. 먼저 승인된 매체 접근·용량과 백업 범위를 확인한다. DB 백업은 일관된 트랜잭션 시점을 보장하고, 고객 VM 디스크는 승인 절차에 따른 정지/스냅샷/응용 정합성 확보 등 선정 방법을 따른다. DB와 VM을 잇는 식별 관계·시점 메타데이터를 백업 집합에 묶고 체크섬/복원 판독성 검사를 수행한다. 도중 변경·매체 오류·부분 성공은 실패/미완료로 기록하고 집합을 복구 기준으로 승격하지 않는다. 고객 VM·디스크가 손실될 위험이 있으면 작업을 멈추고 원본 보존을 유지한다.
- **책임·의존 계약:** 백업 담당이 범위·매체·정합성을 소유하고 FS-026/027이 기록을 제공한다. E 기본 수단에서는 대상별 매체·정합성·복구 가능성을 먼저 확인한다. FS-048 보존 자동화와 FS-053 운영 복구 목표 전체는 R2 후속 연결이며 기본 백업을 막는 순환 선행이 아니다. 미정 매체/목표는 그 범위 실행 전에 확인한다.
- **코드동작확인 Test방식:** 정상·매체 불가·중간 실패·백업 중 데이터 변경을 시험한다. DB와 디스크의 관계·시점이 일치하고 불완전 집합은 복구 성공으로 표시되지 않는지 검증자 복원 시험과 연결한다.
- **코드동작확인 로깅방식:** 운영 감사에 범위 참조·집합 식별·시작/완료·완전성·매체 오류를 기록한다. 기술 로그에는 단계와 오류만 남기며 민감 경로·데이터 내용은 제외한다. 체크섬/DB 검사 결과를 FS-053 복원 증거와 대조한다.
- **완료·반환 증거:** 백업 범위·선정 정합성 방법·별도 매체 참조·완전성·실제 복원 연결·미확정 정책을 반환한다.

<a id="fs-053"></a>
### FS-053 DB·고객 VM 복원·복구 검증

- **목적:** 보존된 집합에서 업무 데이터·VM/디스크 관계와 고객 접근을 격리 환경에서 실제 복구한다.
- **추가 범위:** 권한 있는 복구 절차, 집합 무결성 사전 확인, 복원 후 업무·게스트 검증, 측정 기록.
- **수정 범위:** 복구 목표는 측정치와 승인 정책으로 비교하며 제안 목표를 확정 수치로 사용하지 않는다.
- **삭제 범위:** 운영 원본을 덮어쓰거나 복원 성공을 DB 기동만으로 판정하는 것.
- **goal:** 백업 DB·작업 매핑·고객 VM/디스크를 일치시켜 격리 대상에서 부팅·접근·업무 상태를 확인한다.
- **non-goal:** 무검증 복사본을 운영에 즉시 전환하거나 미확정 RPO/RTO 달성을 선언하는 것.
- **목표-input:** `backup_set_ref`는 검증할 백업 집합(FS-052 제공); `restore_scope`는 대상·영향(운영자 승인 제공); `recovery_target`은 승인된 데이터 시점/시간 기준(결정 기록 제공); `restore_authority`는 실행 승인 문맥(관리자 제공).
- **목표-output:** `restored_state`는 DB·작업/VM 매핑 결과(검증자 수신); `access_result`는 게스트 부팅/접근 확인(운영자 수신); `measured_recovery`는 관측 손실 구간·소요(책임자 수신); `unresolved_items`는 미복구 항목(운영자 수신).
- **구현 동작:** 적용은 R2다. 먼저 승인·격리 대상·백업 집합의 체크섬과 구성원 관계를 검증한다. 업무 DB와 고객 디스크를 대응 시점/관계로 복원하고 스키마·작업·VM 식별 관계를 대조한다. 게스트 부팅과 선정된 접근 확인을 수행한 뒤 측정 시점·소요·미복구 항목을 기록한다. 무결성 불일치, 매핑 누락, 접근 실패는 복구 성공으로 합치지 않고 원본은 격리/보호한다. 운영 전환은 별도 승인 절차와 일관성 검증이 완료될 때까지 중단한다.
- **책임·의존 계약:** 복구 담당자는 FS-052 백업 집합과 FS-050 안전한 비밀 참조를 소비하고 실제 VM 접근 검증을 책임진다. 목표 기준은 G2에서 선정·측정되어야 한다.
- **코드동작확인 Test방식:** 격리 환경에서 정상/손상/누락 구성원 집합, DB·VM·디스크 연결, 작업 원장 관계, 게스트 부팅/SSH 또는 승인 접근 경로를 확인한다. 측정 결과를 승인 목표와 비교하고 운영 원본이 바뀌지 않는지 검사한다.
- **코드동작확인 로깅방식:** 운영 감사에 집합·대상 참조·승인·시작/완료·무결성·접근·미복구 의미를 기록한다. 기술 로그는 단계·오류 추적만 기록한다. 복구 전후 정제 증거와 목표 측정을 대조하고 데이터·주소·비밀 원문은 제외한다.
- **완료·반환 증거:** 실제 격리 복원 결과, DB/디스크 관계·접근 검증, 측정된 손실/시간, 남은 미복구 항목과 승인된 목표 대비를 반환한다.

<a id="fs-054"></a>
### FS-054 릴리스 배포·롤백

- **목적:** 잠금·검증된 release를 호환 가능한 순서로 배포하고 실패 시 코드와 DB 상태가 맞는 복귀 경로를 증명한다.
- **추가 범위:** release manifest·체크섬 확인, migration 선행조건·health 판정, 이전 release 전환 및 결과 기록.
- **수정 범위:** DB 변경은 expand/contract 등 호환 전략을 우선하고 파괴적 migration은 검증된 백업·복원 경로가 있을 때만 진행한다.
- **삭제 범위:** 코드만 되돌린 뒤 호환성 확인 없이 롤백 완료로 표시하는 것.
- **goal:** 배포 중단·health 실패·스키마 불호환을 안전하게 감지하고 실제 서비스/DB 상태를 확인해 복귀한다.
- **non-goal:** 스키마를 자동으로 위험하게 역변환하거나 release를 수동 편집해 맞추는 것.
- **목표-input:** `release_artifact`는 코드/의존성/체크섬/manifest(빌드 책임자 제공); `deployment_config`는 대상 환경·역할(운영자 제공); `migration_plan`은 순서·호환·복원 조건(DB 담당 제공); `rollback_target`은 검증된 이전 release(배포 이력 제공).
- **목표-output:** `deployment_state`는 적용 release·health·migration 결과(운영자 수신); `rollback_result`는 전환·DB 적합성·서비스 재확인(운영 책임자 수신); `deployment_blockers`는 안전한 진행 불가 이유(승인 담당 수신).
- **구현 동작:** 적용은 R1에서 배포 절차를 준비하고 R2에서 장애·복구를 실제 검증한다. manifest/체크섬·mode·대상·호환 migration 선조건을 점검한 뒤 승인된 순서로 schema를 먼저 확장하고 코드 release를 전환한다. health와 대표 업무 흐름을 확인한 후에만 배포 완료로 기록한다. 단계 중 중단은 어느 변경이 반영됐는지 식별하고 재실행 가능성을 검증한다. 실패 시 이전 코드를 가리키기 전에 DB schema가 이전 코드와 호환되는지 판정한다. 불호환이면 무리한 downgrade를 하지 않고 격리·복원 계획을 실행해 실제 DB와 서비스 health를 다시 확인한다. 파괴적 변경은 복원 집합과 FS-053 복구 검증 없이 차단한다.
- **책임·의존 계약:** 배포 책임자가 전환 순서·health·rollback 판정을 소유한다. FS-002 manifest, FS-057 schema revision, FS-052 백업, FS-053 복원 증거와 연결한다. 런타임 비밀은 안전한 참조만 받는다.
- **코드동작확인 Test방식:** 정상 배포·체크섬 불일치·health 실패·중간 중단·이전 코드 전환·호환/비호환 schema를 시험한다. 코드를 되돌린 뒤 schema·데이터·업무 동작이 맞아야 완료이며, 비호환/복원 불가는 차단되는지 관찰한다.
- **코드동작확인 로깅방식:** 감사에 이전/대상 release·승인·검사 단계·migration 참조·전환/차단·health 결과를 남긴다. 기술 로그는 오류·추적만 기록한다. 배포물 체크섬·실제 응답·DB revision 증거를 대조하고 비밀 설정·SQL 본문은 제외한다.
- **완료·반환 증거:** 배포 순서, health 결과, 중단 지점, 이전 코드와 schema 호환 또는 복원 후 상태, 남은 위험을 반환한다.

<a id="fs-055"></a>
### FS-055 운영 부하·용량·한도 확인

- **목적:** 해당 환경 실측으로 회원·VM·동시 작업·요청 한도를 판정한다.
- **추가 범위:** 재현 가능한 부하 프로필, 자원·대기·오류·지연 관찰과 근거 기반 한도 제안.
- **수정 범위:** G1 측정 환경을 확인하고 R3에서 승인 기준에 맞춰 반복한다.
- **삭제 범위:** 모의 처리량을 실제 인프라 용량으로 외삽하거나 선정 제안 수치를 실측 결과처럼 표현하는 것.
- **goal:** 시험 입력·환경·release·관찰값·제한 근거를 연결해 운영 한도 결정을 지원한다.
- **non-goal:** 기준 미정 상태에서 목표 수치나 서비스 보장을 확정하는 것.
- **목표-input:** `load_profile`은 요청·동시 작업·자원 조합의 의미(시험 담당 제공); `resource_budget`은 실측 자원 여유(FS-001 제공); `acceptance_policy`는 승인 지연/오류/용량 의미(운영 결정 제공); `test_scope`는 모의/실제 경계(환경 설정 제공).
- **목표-output:** `measurement_report`는 처리·지연·오류·자원·대기 변화(운영자 수신); `capacity_assessment`는 목표 충족/제한 이유(결정자 수신); `recommended_limits`는 근거가 있는 제한(서비스 운영자 수신).
- **구현 동작:** 적용은 G1 시험 계획, R3 측정이다. 먼저 대상 자원·라이선스·mode·부하 생성 범위·승인 기준을 확인한다. 기준선 관찰 후 단계적으로 부하를 높이고 API·worker·DB·디스크·VM 작업 대기·오류를 함께 기록한다. 안정성 회복까지 관찰하고 중단 조건에 닿으면 부하를 멈추며 진행 중 작업을 정리/확인한다. 모의와 실제 환경 결과를 별도 보고한다. 자원 미확인이나 합격 기준 부재는 성공 대신 조건 대기로 남기며, 최종 한도는 관측 범위와 불확실성을 명시한다.
- **책임·의존 계약:** 용량 검증 담당자가 프로필·측정·판정을 소유한다. FS-001 실습 자원, FS-049 감시, P/E 작업 처리와 의존한다. 실습 PC CPU·디스크·라이선스가 확인 전 차단 조건이다.
- **코드동작확인 Test방식:** 기준·경계·한도 초과·장기 대기·부하 제거 후 회복을 실제 대상에서 관찰한다. 모의/실제 라벨과 자원 측정이 일치하고 미정 승인 기준은 합격으로 처리하지 않는지 확인한다.
- **코드동작확인 로깅방식:** 측정 기록에 프로필·환경·시각·release·자원·관찰·중단 사유를 남긴다. 기술 로그와 감시 지표를 상관시켜 정제 보고서로 대조하고 개인 요청 원문·비밀은 제외한다.
- **완료·반환 증거:** 재현 프로필, 실제 관찰 범위, 한계·중단, 제안 가능한 운영 한도와 미확정 승인 기준을 반환한다.

<a id="fs-056"></a>
### FS-056 기능검증 증거·공개자료 정리

- **목적:** 기능별 검증 상태·재현 근거·범위 한계를 추적하며 공개 가능한 증거만 보존한다.
- **추가 범위:** 기능/사례 ID와 기대·관찰·결과·환경·release·정제 증거 연결, 커버리지 누락 점검.
- **수정 범위:** 보고서는 기술 로그·감사 원장·실습 증거를 각각 원천으로 참조하고 결과를 섞지 않는다.
- **삭제 범위:** 미실행/조건 대기를 통과로 바꾸거나 원본 운영 로그를 Git에 저장하는 것.
- **goal:** 모든 완료 주장에 재현 가능한 관찰 근거와 검증 한계가 따라온다.
- **non-goal:** 성공 기록을 실제 코드·서비스 검증과 같은 것으로 간주하는 것.
- **목표-input:** `feature_test_records`는 기능/사례·기대/관찰·결과(검증 담당 제공); `source_evidence`는 로그·DB·화면·실습 자료 참조(각 원천 제공); `redaction_policy`는 공개 제외 기준(보안 규칙 제공); `runtime_context`는 환경·release·설정 버전(배포/실습 제공).
- **목표-output:** `verified_evidence_refs`는 정제 자료 참조(검토자 수신); `coverage_report`는 통과·실패·미실행·대기(책임자 수신); `reproduction_notes`는 전제·순서·한계(후속 검증자 수신).
- **구현 동작:** 적용은 P4의 Prototype 결과와 E/R 단계 증거를 각각 수집한다. 기능목록의 각 ID를 사례 기록에 연결하고 코드 Test 결과, 문서 검증, 실제 서비스/실습 관찰을 구분한다. 출처 참조가 열리는지·기능/사례·release/mode·실행시각이 연결되는지 확인하고 민감정보를 제거한 사본만 공개 자료로 남긴다. 누락 링크·민감정보·조건 대기·미실행은 커버리지에 그대로 반영하며 성공으로 집계하지 않는다. 원본 운영 로그는 저장소에 복사하지 않는다.
- **책임·의존 계약:** 검증 담당자가 증거 맵과 공개 범위를 소유한다. 각 기능 담당은 원천 Test/감사/실습 결과를 제공한다. FS-027 기술 로그와 FS-026 원장은 다른 증거 종류로 참조된다.
- **코드동작확인 Test방식:** 기능목록과 사례 연결 완전성, 깨진 링크, 결과 상태 구분, mode 혼동, 재현 전제, 민감정보 검색을 검사한다. 증거가 없는 성공·테스트하지 않은 기능의 성공 표시가 거부되는지 확인한다.
- **코드동작확인 로깅방식:** 정제 보고서에는 기능/사례 식별·출처 종류·실행/정제 결과·환경·release 참조를 남긴다. 원본 로그는 외부 저장을 금지하고 기술·감사·실습 출처를 각각 대조 가능한 참조로 연결한다.
- **완료·반환 증거:** 커버리지 표, 재현 전제, 정제 검사, 미실행/대기 목록과 범위 한계를 반환한다.

<a id="fs-057"></a>
### FS-057 DB 스키마 구성·마이그레이션

- **목적:** 업무·세션·작업·감사와 모의 저장소에 필요한 구조·제약·권한을 버전 관리한다.
- **추가 범위:** schema revision 추적, 순서화된 migration, 외래키/고유 제약 및 DB 역할 검증.
- **수정 범위:** 모든 변경은 release 호환 계획과 연계하고 업무 DB와 모의 DB 권한 경계를 별도로 유지한다.
- **삭제 범위:** 수동 무기록 schema 변경, 앱 실행 시 무검토 파괴적 migration, 모의 계정의 업무 DB 접근.
- **goal:** 빈/기존 DB의 구조 전이를 재현하고 실패 시 적용 revision과 부분 상태를 정확히 드러낸다.
- **non-goal:** FS-054와 분리된 독립 downgrade 보장 또는 모의 데이터의 업무 저장소 이관.
- **목표-input:** `migration_set`은 release별 순서/구조 변경(배포 제공); `current_schema_revision`은 기존 revision(저장소 관찰 제공); `database_role`은 업무/모의 경계와 권한(DB 관리자 제공); `migration_authority`는 구조 변경 실행 문맥(배포 담당 제공).
- **목표-output:** `applied_schema_revision`은 실제 구조 버전(배포·운영자 수신); `migration_result`는 적용/기존/실패/보류(배포 게이트 수신); `constraints_and_permissions`는 제약·계정 경계 결과(검증자 수신).
- **구현 동작:** 적용은 P1 공통 기반이며 E/R migration에도 지속 적용한다. 대상 DB identity·권한·기존 revision을 읽고 순서·선행조건·호환 계획을 검증한다. 업무와 모의 저장소를 별도 계정/namespace로 처리하고 요구 제약을 적용한다. migration은 중복 실행 안전성을 확인하고 각 단계 성공 뒤 revision을 기록한다. 중간 실패는 부분 적용 상태를 진단해 임의로 다음 단계를 건너뛰지 않으며 재개/복구 계획을 FS-054와 조율한다. 기존 데이터 변환·파괴 변경은 호환 절차와 백업 검증이 없으면 차단한다.
- **책임·의존 계약:** 업무 모듈이 구조·제약·권한 의미를 제안하고 통합 담당이 migration 버전·순서·실행을 직렬 관리한다. P1 초기 준비는 공통 계약·DB 역할·FS-025 분리에 따라 수행하며 Audit 서비스 완료를 선행으로 요구하지 않는다. FS-026이 준비된 schema를 소비한다. 기존 데이터 변경 시에는 호환/복구 원칙을 적용하고 R1/R2의 FS-054 전체 배포 완료를 초기 준비 선행으로 요구하지 않는다.
- **코드동작확인 Test방식:** 빈 테스트 DB·기존 revision·반복 실행·중간 실패·순서 오류·권한 부족·업무/모의 혼선을 확인한다. 같은 migration 재실행이 중복 구조를 만들지 않고 업무 세션 공유/멱등 제약과 앱 원장 권한이 유지되는지 관찰한다.
- **코드동작확인 로깅방식:** 기술/운영 기록에 migration 참조·DB 역할·revision 전후·단계·결과·실패 분류를 남긴다. 비밀 연결값·SQL 본문은 제외한다. 실제 schema·제약·계정 권한을 Test 증거와 대조한다.
- **완료·반환 증거:** 빈/기존 DB 전이, 재실행·실패 처리, 제약·계정 경계, 배포 호환/복구 연결 및 남은 migration 제한을 반환한다.
