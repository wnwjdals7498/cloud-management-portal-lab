# 기능별 구현 상세계획과 병렬 인계

> 2026-10-01 · 기준: [기능목록](../feature-list.md), [기능 명세서](../function-specification.md), [1차 구현 계획](../../implementation-plan-v1.md). 이 문서는 구현 작업의 범위와 확인 기준이며 현재 기능 구현 완료를 의미하지 않는다.

[58개 기능별 상세계획](feature-map.md)에서 해당 ID를 찾고, [병렬 실행·공유 계약·반환 방식](parallel-execution.md)을 함께 적용한다. 상세계획은 GPT-6 Luna 서브에이전트 3개가 작성했고 통합 담당이 교차검토·의존 경계를 보완했다.

## 인계 원칙

인계 목표는 기능의 동작·책임·계약·증거다. 파일명은 구현자가 경계 안에서 정할 배치 선택이며 ‘어느 파일에 무엇을 추가/수정/삭제’하는 명령을 목표나 완료 기준으로 사용하지 않는다.

각 기능은 다음 항목으로 인계한다.

| 항목 | 지정할 내용 |
| --- | --- |
| 목적 | 해결할 사용자/운영 문제와 기대 동작 |
| 추가/수정/삭제범위 | 추가 책임·변경 가능한 기존 계약·제거/제외할 동작의 경계. 착수 시 기존 구현 여부와 실제 계약을 확인 |
| goal / non-goal | 완료해야 할 결과와 이번 기능에서 확장하지 않을 책임 |
| 목표-input / 목표-output | 필드 또는 문맥의 의미·공급자/수신자·필수 조건. 직접 예제 값은 쓰지 않음 |
| 구현 동작 | 실행 순서·검증·트랜잭션/동시성·상태 전이·실패/재기동 경계 |
| 책임·의존 계약 | 단일 소유 모듈과 호출자/제공자, 필요한 선행 기능·미정 게이트 |
| 코드동작확인 Test방식 | 정상·거부·경계·장애와 적용 가능한 중복/동시성/재기동 사례, 합격 관찰 |
| 코드동작확인 로깅방식 | 사건·추적·감사/기술 구분·마스킹·기대 로그와 상태를 대조하는 방법 |
| 완료·반환 증거 | 바뀐 동작/계약 요약, 실제 Test 결과, 정제 증거, 남은 보류 |

상세계획이 원문과 다르면 원문을 우선 확인하고 충돌을 통합 담당자에게 넘긴다. 제안 수치·미정 환경·조건부 기능을 임의로 확정하지 않는다.

## 통합 확인 기준

- 입력·출력은 의미와 공급/수신 주체로 작성한다. 수치·환경·모의 설정은 원문 정책/제안으로 관리하며 직접 값을 상세 인계에 넣지 않는다.
- 신청 한도와 멱등을 원자적으로 처리하고, 동일 event ID의 상이 내용은 격리한다. 외부 호출 중 DB 잠금은 유지하지 않는다.
- 상호 TLS는 확정된 방향이다. 실제 외부 멱등·알림 전달·PG 인증 방법은 검증된 상대 계약에 한정한다.
- 호출 경계의 계약/기본 제공자와 해당 기능의 전체 운영 완료를 구분한다. Audit append는 P1 계정 감사 전 준비하고 P2 업무 전이로 확장한다. R2 감시·보존·전체 복구 검증을 P/E 최소 기능의 순환 선행으로 요구하지 않는다.
- 작성 당시 코드 없는 상태의 추가 책임과 향후 변경/배제 동작을 구분했다. 다음 작업은 [검증 기록](../../operations/prototype-progress.md)과 기존 코드를 확인하며, 삭제 범위를 실제 원장·역사 삭제 명령으로 해석하지 않는다.
- 계획 검증과 실제 코드/실습 Test를 구분한다. 조건 대기 기능은 합격으로 기록하지 않는다.
