# 기능 명세서

> 2026-10-01 · [기능목록](feature-list.md)에서 추출한 기능의 구현·검증 목표. 현재 Prototype의 실행 결과는 [검증 기록](../operations/prototype-progress.md)을 따른다. E·R 단계는 미실행이며 이 명세 작성 자체를 기능 완료로 판단하지 않는다.

구현 방법은 [기능별 상세계획](implementation-details/feature-map.md)과 [병렬 인계·통합](implementation-details/parallel-execution.md)에 연결한다. 공통 Audit append는 초기 계정 감사 전에 준비하고 업무 트랜잭션 감사로 확장한다.

## 작성 기준

- 기준 문서: [작업 지침](../../AGENTS.md), [참조 안내](README.md), [1차 구현 계획](../implementation-plan-v1.md), [UI 가이드](../ui/guide.md). 기존 확정 결정과 모의/실제 경계를 유지한다.
- 목표-input/output은 **필드명과 각 값의 의미**만 정의한다. 계정·주소·사양·확률·지연·단가·기간 등 직접 값과 JSON 예제는 넣지 않는다.
- 필드명은 역할을 설명하는 논리 명세다. 실제 API/schema 확정은 원문 계약과 맞춰 수행하며 새 응답 wrapper나 별도 제품 범위를 추가하지 않는다.
- 입력에는 사용자 요청뿐 아니라 설정·세션 문맥·외부 결과·시각·절차 증거도 포함한다. 원래 없는 입력은 ‘없음’으로 표시한다.
- ‘공통 문맥’은 서버가 확인한 행위자 신원·역할·요청 추적·실행환경이다. 브라우저가 보낸 사용자 ID를 신원으로 신뢰하지 않는다.
- ‘공통 결과’는 요청/작업 식별, 접수·처리 여부, 실패/보류 이유, 실행환경, 관찰 시각이다. 관련 없는 필드는 생략한다. 접수와 완료, 관찰값과 확정 상태를 구분한다.
- P/E/R은 [단계](stages.md)의 최초 적용 시점이다. 절차 기능은 운영자의 실행·검증 산출물까지 정의하며 자동 구축 서비스로 가정하지 않는다.

## Test·로깅 공통 방식

- **단위:** 정책·계산·상태 전이를 고정 시각/의존성으로 확인한다. **통합:** 실제 테스트 MySQL에서 제약·트랜잭션·동시성·재기동을 확인한다.
- **계약:** 독립 schema·fixture로 HTTP/통지 변환을 확인한다. **화면:** 역할별 브라우저 흐름·반응형·키보드·표시 의미를 확인한다. **실습:** 실제 서비스/VM 관찰값과 결과를 대조한다.
- 모의 시나리오는 고정 seed·저장된 추첨·개발 CLI 강제 지정으로 분기를 확인한다. 실제 인프라 Test를 모의 결과로 통과시키지 않는다.
- 기능확인 로깅은 **기술 로그**, **감사 원장**, **Test 결과 기록**을 구분한다. 아래 각 항목은 기술/감사에 남길 사건·필드를 지정한다.
- 기술 로그의 공통 항목은 UTC 시각·수준·서비스·release·mode·요청/작업 추적·시도·사건·소요 시간·오류 분류다. 감사는 행위자·대상·작업·허용/거부·변경 이력이다.
- Test 결과에는 `feature_id`(기능 식별), `test_case_id`(검증 사례 식별), `result`(통과/실패/미실행/조건 대기), `expected_summary`(기대 의미), `observed_summary`(관찰 의미), `evidence_ref`(정제 증거 위치), 실행 시각·release·mode를 남긴다. 미실행과 조건 대기를 성공으로 기록하지 않는다.
- 기능별 확인은 동일 추적 ID의 로그·DB·외부 관찰·Test 기록을 대조한다. 로그 한 줄만으로 완료를 판정하지 않는다.
- 비밀번호·세션/CSRF 원문·토큰·개인키·전체 본문·내부 주소를 로그와 공개 증거에 넣지 않는다. 입력·출력 설명에 비밀값의 역할이 있어도 실제 비밀은 기록하지 않는다.
- 저장·보존·회전은 [구현 및 운영 규칙](coding-and-operations.md)을 따른다. 아래 로깅 방식은 사용자 데이터 전체를 덤프하는 요구가 아니다.

## 환경·계정·화면

근거: [단계](stages.md), [구조](architecture.md), [계약](contracts.md), 원문 1~6절.

<a id="fs-001"></a>
### FS-001 실행환경·설정·자원 게이트 확인

- **목표:** 단계에 필요한 환경만 확인하고 미확인 자원으로 통과하지 않는다.
- **목표-input:** `gate`: 확인할 단계; `environment_inventory`: 제품·확장·자원·접속의 확인 정보; `required_settings`: 해당 단계의 필수 설정 의미; `evidence`: 확인 근거.
- **목표-output:** `readiness`: 착수 가능 여부; `missing_items`: 미확인/불충족 항목과 이유; `verified_inventory`: 확인된 환경 목록.
- **기능확인 Test 방식:** 확장 누락·DB 연결 실패·잘못된 설정·자원 미확인 사례를 주입해 차단을 확인한다. 개발 PC와 실습 PC의 정보가 섞이지 않는지 검토한다.
- **기능확인 로깅 방식:** 기술 로그에 게이트·검사 항목·판정·근거 참조를 남긴다. 비밀 연결값 없이 Test의 대기/실패 원인과 대조한다.

<a id="fs-002"></a>
### FS-002 의존성 잠금·실행환경 명세

- **목표:** 동일한 의존성과 실행환경으로 설치·배포를 재현한다.
- **목표-input:** `dependency_lock`: 설치할 의존성의 확정 버전 관계; `runtime_inventory`: 검증된 제품·확장 버전; `artifact_checksums`: 배포물 일치 확인 정보.
- **목표-output:** `runtime_manifest`: 실행환경과 잠금파일의 연결; `consistency_result`: 의존성·실행환경 일치 여부와 차이.
- **기능확인 Test 방식:** 깨끗한 환경에서 잠금 기준 설치를 확인하고, 호환하지 않는 확장/변경된 배포물을 탐지한다.
- **기능확인 로깅 방식:** 기술 로그에 manifest·release 참조, 검사 결과·불일치 종류를 남긴다. 설치 결과와 잠금파일 근거를 Test 기록에 연결한다.

<a id="fs-003"></a>
### FS-003 초기 관리자·회원 계정 준비

- **목표:** 공개 가입 없이 초기 테스트 계정을 준비한다.
- **목표-input:** `account_definitions`: 계정의 로그인 식별·역할·초기 인증정보 의미; `execution_context`: 계정 준비 권한과 환경.
- **목표-output:** `account_refs`: 준비된 계정 식별; `assigned_roles`: 실제 부여된 역할; `creation_result`: 생성·기존 계정 확인·거부 결과.
- **기능확인 Test 방식:** 초기 준비·재실행·잘못된 역할을 확인하고, 공개 가입 경로가 열리지 않는지 검사한다.
- **기능확인 로깅 방식:** 감사에 계정 준비 행위자·대상 참조·역할·결과를 남긴다. 인증정보 원문 없이 생성/재실행 이력을 대조한다.

<a id="fs-004"></a>
### FS-004 로그인·로그아웃·현재 사용자

- **목표:** API 세션으로 신원을 확인하고 종료된 세션을 사용할 수 없게 한다.
- **목표-input:** `login_identifier`: 계정을 찾는 로그인 식별; `credential`: 계정 증명 정보; `session_context`: 현재 인증 문맥; `auth_action`: 로그인·종료·신원 조회 요청의 의미.
- **목표-output:** `authentication_result`: 신원 확인 여부; `user_context`: 공개 가능한 신원·역할; `session_transition`: 세션 생성/재발급/종료 여부. 세션 원문은 별도 안전한 전송 경계에서 처리한다.
- **기능확인 Test 방식:** 정상/잘못된 인증·미인증 조회·세션 재발급·로그아웃 후 재사용을 확인한다. 콘솔별 쿠키 격리와 병렬 API 세션도 확인한다.
- **기능확인 로깅 방식:** 감사에 인증 성공/거부·세션 종료·역할을 기록한다. 기술 로그에는 이유 분류만 남기고 비밀번호·쿠키·세션 식별 원문은 제외한다.

<a id="fs-005"></a>
### FS-005 CSRF 준비·검증

- **목표:** 인증 문맥에 맞는 요청 위조 방지 검증을 적용한다.
- **목표-input:** `session_context`: 검증 기준 세션; `csrf_proof`: 요청의 세션 연계 증명; `request_method`: 변경 요청인지 판별하는 정보.
- **목표-output:** `csrf_metadata`: 브라우저가 증명을 제출할 방법; `validation_result`: 요청 허용 여부와 거부 이유. 증명값은 전송 시에만 제공한다.
- **기능확인 Test 방식:** 증명 누락·변조·다른 세션·만료/재발급과 정상 요청을 비교한다. 내부 완료 통지는 사용자 CSRF 대신 서비스 인증을 적용하는지 확인한다.
- **기능확인 로깅 방식:** 기술 로그에 검증 여부·실패 분류·요청 추적을 남긴다. 증명값을 기록하지 않고 거부된 요청의 업무 변경 없음과 대조한다.

<a id="fs-006"></a>
### FS-006 역할·소유권 검사

- **목표:** 회원은 본인 자원, 관리자는 허용된 전체 업무만 접근한다.
- **목표-input:** `actor_context`: 서버 검증 신원·역할; `resource_ref`: 조회/변경 대상; `requested_action`: 요청 작업; `ownership`: 저장된 소유 관계.
- **목표-output:** `authorization_result`: 허용 여부; `visible_scope`: 조회 가능 범위; `denial_reason`: 공개 가능한 거부 분류.
- **기능확인 Test 방식:** 다른 회원의 식별자로 직접 API 요청·관리자 경로 우회·모의 UI 숨김 우회를 시도한다. 조회·변경·청구·기록 모두 동일 경계를 확인한다.
- **기능확인 로깅 방식:** 감사에 행위자·대상 참조·작업·허용/거부를 남긴다. 거부 시 결과 노출과 DB 변경이 없음을 Test 증거로 확인한다.

<a id="fs-007"></a>
### FS-007 고객·관리자 개요 화면

- **목표:** 권한 범위의 현재 상태·문제·최근 작업을 보여준다.
- **목표-input:** `user_context`: 화면 역할; `summary_data`: 허용 범위 VM·작업·이후 청구/인프라 요약; `observed_at`: 데이터 기준 시각.
- **목표-output:** `overview_view`: 역할별 요약·문제·최근 작업; `freshness_indicator`: 최신성·조회 실패 표시; `available_navigation`: 해당 단계의 허용 메뉴.
- **기능확인 Test 방식:** 두 역할·빈 데이터·진행/실패·오래된 값·API 오류를 화면에서 확인한다. 작은 화면·키보드와 색 이외 상태 문구도 검사한다.
- **기능확인 로깅 방식:** 기술 로그에 요약 조회 성공/실패·범위·기준 시각을 남긴다. 화면 캡처와 API 응답 의미를 Test에서 대조하며 개인 데이터는 정제한다.

<a id="fs-008"></a>
### FS-008 VM 목록·상세 조회

- **목표:** 소유 범위 VM의 사양·작업·관찰 상태를 구분해 보여준다.
- **목표-input:** `actor_context`: 조회 권한; `vm_ref`: 상세 대상; `list_scope`: 조회 조건·페이지 범위; `state_observation`: 저장/외부 조회 결과.
- **목표-output:** `vm_view`: 소유·적용 사양·전원/게스트 관찰·작업 상태; `allowed_actions`: 현재 가능한 작업; `freshness`: 마지막 확인과 오류 의미; `mode`: 자원의 실행환경 구분.
- **기능확인 Test 방식:** 본인/관리자 조회·타인 거부·빈 목록·외부 조회 실패·접수와 완료 구분을 확인한다. 모의 VM에 실제 접속 가능 표시가 없는지도 확인한다.
- **기능확인 로깅 방식:** 기술 로그에 조회 대상 참조·범위·관찰 신선도·결과를 남긴다. 민감한 접속주소 없이 화면과 저장값을 대조한다.

<a id="fs-009"></a>
### FS-009 작업 기록·상세 조회

- **목표:** 요청부터 각 시도·결과·재확인까지의 흐름을 추적한다.
- **목표-input:** `actor_context`: 조회 권한; `job_ref`: 대상 작업; `history_scope`: 시간·상태·대상·페이지 조건의 의미.
- **목표-output:** `job_history`: 요청·시도·단계·결과·오류·통지·관찰 시각; `recovery_context`: 재확인/재시도 가능 정보와 미확정 이유.
- **기능확인 Test 방식:** 회원 간 기록 차단, 관리자 전체 조회, 지연·중복·실패·재시도 타임라인을 DB와 대조한다.
- **기능확인 로깅 방식:** 기술 로그에 조회 범위·작업 참조·결과를 남긴다. Test 기록은 타임라인과 동일 작업의 사건 로그·inbox·attempt를 연결한다.

<a id="fs-010"></a>
### FS-010 VM 사양 조회·관리

- **목표:** 서버가 허용한 사양에서 신청하게 하고 변경 이력을 보존한다.
- **목표-input:** `profile_ref`: 사양 식별; `profile_definition`: CPU·메모리·디스크·허용 네트워크의 의미; `availability`: 신청 가능 상태; `actor_context`: 조회/관리 권한.
- **목표-output:** `selectable_profiles`: 허용 사양 목록; `profile_revision`: 사양 정의·가용 상태 변경 이력; `validation_result`: 값의 허용 범위 판정.
- **기능확인 Test 방식:** Prototype은 고정 목록 조회, 확장은 관리자 관리·회원 변경 거부·미허용 사양 거부를 확인한다. 변경 후 기존 VM 적용 이력이 바뀌지 않는지 검사한다.
- **기능확인 로깅 방식:** 감사에 사양 참조·변경 항목·버전·행위자·판정을 남긴다. 내부 네트워크 값을 공개하지 않고 신청 당시 사양과 대조한다.

<a id="fs-011"></a>
### FS-011 관리자 회원 관리

- **목표:** 관리자가 테스트 회원을 생성·조회·수정한다.
- **목표-input:** `actor_context`: 관리자 권한; `member_ref`: 대상 회원; `member_changes`: 허용된 계정 정보 변경의 의미.
- **목표-output:** `member_view`: 허용 계정 정보; `management_result`: 처리 여부·거부 이유; `account_history`: 계정 변경 이력.
- **기능확인 Test 방식:** 관리자 처리·회원의 직접 요청 거부·중복 로그인 식별·잘못된 역할 변경을 확인한다. 변경 가능 필드는 구현 전에 계약으로 한정한다.
- **기능확인 로깅 방식:** 감사에 관리자·회원 참조·변경 필드 종류·결과를 남긴다. 자격 증명이나 개인 정보 전체를 기록하지 않는다.

## 신청·작업·통지

근거: [계약](contracts.md), 원문 6·8절. 공통 인증·권한·오류 처리는 FS-004~006을 적용한다.

<a id="fs-012"></a>
### FS-012 VM 생성 신청·작업 등록

- **목표:** 승인 대기 없이 신청을 등록하고 실행 요청을 남긴다.
- **목표-input:** `profile_id`: 허용 사양 선택; `idempotency_key`: 동일 제출을 식별하는 키; `actor_context`: 신청자 신원·허용량; `mode`: 실행 대상 환경.
- **목표-output:** `job_id`: 작업 추적 식별; `vm_id`: 서버 생성 논리 VM 식별; `acceptance_status`: 접수·진행 단계; `request_id`: 요청 추적; 등록 원장·outbox·감사.
- **기능확인 Test 방식:** 정상·잘못된 사양·허용량 초과·트랜잭션 중간 실패를 확인한다. VM·작업·outbox·감사가 함께 저장되거나 함께 취소되는지 검사한다.
- **기능확인 로깅 방식:** 기술 로그와 감사에 신청 접수/거부·사양 참조·작업/VM 참조·모드를 남긴다. 접수 로그를 실제 생성 성공으로 기록하지 않는다.

<a id="fs-013"></a>
### FS-013 요청 중복 방지

- **목표:** 반복 제출이 새로운 VM 작업을 중복 생성하지 않게 한다.
- **목표-input:** `request_identity`: 행위자·작업 종류·멱등 키의 관계; `body_fingerprint`: 제출 내용 일치 판정 정보; `existing_request`: 저장된 최초 제출.
- **목표-output:** `request_resolution`: 신규/기존/충돌 처리 의미; `original_job_ref`: 기존 작업 연결; `conflict_reason`: 같은 키에 다른 내용이 들어온 이유.
- **기능확인 Test 방식:** 순차·동시 중복, 같은 키의 변경된 내용, 다른 회원/작업 종류를 검사한다. 작업·outbox·외부 생성의 중복이 없는지 확인한다.
- **기능확인 로깅 방식:** 기술 로그에 신규·재사용·충돌과 원본 작업 참조를 남긴다. 멱등 키/본문 원문 없이 DB 고유 제약과 외부 요청 이력을 대조한다.

<a id="fs-014"></a>
### FS-014 outbox 점유·외부 전달

- **목표:** 저장된 외부 요청을 안전하게 점유·전달한다.
- **목표-input:** `outbox_entry`: 전달할 작업·허용 입력; `lease_policy`: 점유 유효기간·회수 조건의 의미; `gateway`: 선택된 외부 adapter.
- **목표-output:** `dispatch_result`: 전달/접수/불명확 결과; `external_job_ref`: 외부 작업 연결; `lease_state`: 점유·해제·회수 상태; 전달 시도 이력.
- **기능확인 Test 방식:** 복수 worker 경합·외부 응답 유실·느린 호출을 확인한다. 한 작업의 유효 점유와 호출 중 DB 잠금 해제, 동일 외부 멱등 키를 검사한다.
- **기능확인 로깅 방식:** 기술 로그에 점유·전달·접수·불명확 사건과 작업·시도·소요시간을 남긴다. 명령행·외부 주소 대신 정제 참조를 기록한다.

<a id="fs-015"></a>
### FS-015 작업 상태 전이·결과 반영

- **목표:** 근거 있는 결과만 작업과 VM에 반영한다.
- **목표-input:** `current_state`: 현재 작업 단계; `verified_event`: 검증된 접수/완료/기한 사건; `attempt_context`: 적용 대상 시도; `vm_observation`: 확인된 VM 상태.
- **목표-output:** `job_state`: 유효한 전이 결과; `vm_applied_state`: 확정 반영된 VM 정보; `transition_result`: 적용·보류·거부 이유; 감사 기록.
- **기능확인 Test 방식:** 허용·금지 전이, 접수만으로 성공하는 오류, 늦은 결과, 종료 결과 충돌을 확인한다. 작업·VM·감사 변경의 원자성을 검사한다.
- **기능확인 로깅 방식:** 감사에 이전/이후 단계·근거 사건·시도·대상 참조를 남긴다. 기술 로그의 반영/보류/거부와 실제 DB 전이를 대조한다.

<a id="fs-016"></a>
### FS-016 완료 통지 인증·수신 검증

- **목표:** 등록된 서비스의 일치하는 작업 결과만 수신한다.
- **목표-input:** `service_identity`: 검증할 송신 서비스 신원·출발지; `completion_message`: 사건·작업·외부 대상·시도·결과·관찰시각·오류·환경 의미; `request_mapping`: 접수 기록과 연결.
- **목표-output:** `receipt_result`: 수신 허용 여부; `inbox_ref`: 지속 저장된 통지; `validation_errors`: 신원·schema·작업/대상 불일치 분류.
- **기능확인 Test 방식:** 개발 loopback 제한과 실제 상호 TLS를 각 단계에서 검증한다. 잘못된 서비스 신원·누락 필드·다른 대상·환경을 주입해 업무 반영 전 차단을 확인한다.
- **기능확인 로깅 방식:** 기술 로그에 수신/거부·서비스 역할·작업/사건 참조·검사 결과를 남긴다. 인증 비밀·원문 전체 없이 inbox 보존과 비교한다.

<a id="fs-017"></a>
### FS-017 선행·중복·충돌 통지 처리

- **목표:** 통지 순서와 반복으로 상태가 잘못 덮어써지지 않게 한다.
- **목표-input:** `inbox_event`: 저장된 통지; `event_identity`: 중복 식별; `mapping_state`: 외부 ID 연결 준비 상태; `attempt_and_result`: 현재 시도·확정 결과.
- **목표-output:** `processing_disposition`: 적용·매핑 대기·중복 무시·충돌 격리의 의미; `effective_result`: 실제 업무 반영 여부; 통지 처리 이력.
- **기능확인 Test 방식:** 외부 ID 저장 전 통지, 반복/동시 통지, 이전 시도·종료 결과 충돌, 처리 중 재시작을 확인한다. 최종 업무 효과의 단일 반영을 검사한다.
- **기능확인 로깅 방식:** 기술 로그에 대기·재처리·중복·격리와 사건·시도 참조를 남긴다. 감사 변경 건수와 inbox의 처리 상태를 대조한다.

<a id="fs-018"></a>
### FS-018 외부 상태 관찰·동기화 조회

- **목표:** 화면 요청 시 실제 관찰값과 최신성을 반환한다.
- **목표-input:** `job_or_vm_ref`: 조회 대상; `status_reader`: 모의/실제 조회 경계; `last_observation`: 마지막 확인값·시각; `read_policy`: 연결 한도·실패 처리 의미.
- **목표-output:** `observed_state`: 외부 작업/VM 관찰값; `observed_at`: 확인 기준 시각; `freshness`: 새 값/기존 값의 오래됨; `discrepancy`: 확정 결과와 다른 점.
- **기능확인 Test 방식:** 정상·연결 실패·조회 권한 제한·callback 충돌·병렬 화면 요청을 확인한다. 오래된 값을 최신으로 표시하거나 누락 통지를 자동 성공으로 바꾸지 않는지 검사한다.
- **기능확인 로깅 방식:** 기술 로그에 조회 adapter·대상 참조·시각·소요시간·실패/불일치를 남긴다. 원문 SQL/주소 없이 화면·관찰 원장·callback을 대조한다.

<a id="fs-019"></a>
### FS-019 지연·누락 재확인·명시적 재시도

- **목표:** 불명확한 결과를 실패로 단정하거나 중복 실행하지 않고 복구한다.
- **목표-input:** `job_ref`: 재확인 대상; `deadline_policy`: 대기 기준 의미; `external_evidence`: 접수/실행 관찰 근거; `recovery_action`: 권한 있는 재조회·재통지·새 시도 선택.
- **목표-output:** `reconciliation_state`: 미확정 이유·진행/복구 결과; `retry_attempt`: 허용된 새 시도 이력; `action_guard`: 위험한 재실행 차단 이유.
- **기능확인 Test 방식:** 응답 유실·늦은 완료·누락·재통지를 확인한다. 원래 요청 재전송과 새 시도를 구분하고, 실제 멱등 계약 미확인 시 생성 재실행을 차단한다. 실제 복구 정책은 E1 확정 후 검증한다.
- **기능확인 로깅 방식:** 감사에 복구 행위자·작업·선택 동작·근거·시도 결과를 남긴다. 기술 로그의 대기/재확인 상태를 외부·원장 결과와 대조한다.

<a id="fs-020"></a>
### FS-020 worker 중단·재기동 복구

- **목표:** 프로세스 중단 후 저장된 작업을 유실·중복 없이 이어간다.
- **목표-input:** `persisted_work`: outbox/inbox와 전달 이력; `lease_state`: 만료·유효 점유 정보; `external_receipt`: 외부 접수 확인; `restart_context`: 재기동 환경.
- **목표-output:** `recovered_work`: 회수/이어받은 작업; `remaining_unknowns`: 안전하게 남긴 불명확 결과; `recovery_result`: 유실·중복 여부와 복구 처리.
- **기능확인 Test 방식:** 점유 후·외부 접수 후·통지 반영 전 각각 중단한다. 재기동 후 예정 작업 처리와 기존 외부 작업 재연결, 업무 단일 반영을 확인한다.
- **기능확인 로깅 방식:** 기술 로그에 재기동·lease 회수·기존 접수 재연결·보류를 남긴다. 중단 전후 추적 ID와 DB·모의/실제 대상 수를 대조한다.

## 모의 VMM·공통 기록

근거: [모의 연동](vmm-simulator.md), [구현 및 운영 규칙](coding-and-operations.md), 원문 7~11절.

<a id="fs-021"></a>
### FS-021 모의 응답 범위 설정 검증

- **목표:** 지정 범위를 벗어난 무작위 실행을 시작하지 않는다.
- **목표-input:** `simulation_profile`: 시나리오 가중치·지연 경계·오류 허용목록·중복 규칙·대기 한도; `profile_version`: 설정 추적; `seed_policy`: 재현 방식 의미.
- **목표-output:** `validated_profile`: 실행 가능한 범위; `configuration_errors`: 가중치·순서·상한·허용값 오류; `startup_decision`: 모의 실행 가능 여부.
- **기능확인 Test 방식:** 정상·누락·음수·합계 불일치·경계 역전·미허용 오류·대기 한도 설정을 확인한다. 허용값은 설정 정의에서 가져온다.
- **기능확인 로깅 방식:** 기술 로그에 프로필 버전·검사 항목·기동 허용/거부를 남긴다. 잘못된 설정에서 추첨·통지 실행 없음과 대조한다.

<a id="fs-022"></a>
### FS-022 무작위 추첨·저장·재현

- **목표:** 요청마다 지정 범위에서 한 번 추첨하고 같은 결과를 재현한다.
- **목표-input:** `sim_request`: 모의 작업 식별·입력 의미; `validated_profile`: 허용 시나리오·범위; `random_context`: seed·알고리즘 버전; `saved_draw`: 기존 추첨 유무.
- **목표-output:** `selected_scenario`: 선택한 실행 경로; `scheduled_parameters`: 결정된 지연·오류·통지 규칙; `draw_record`: 재현 가능한 저장 결과·설정 관계.
- **기능확인 Test 방식:** 경계/허용 시나리오 안에서만 추첨되는지 확인하고 고정 문맥으로 재현한다. 중복·재조회·재시작이 재추첨하지 않는지 검사한다. 한 번의 추첨으로 확률 분포를 판정하지 않는다.
- **기능확인 로깅 방식:** 모의 DB에 추첨·seed·알고리즘·프로필 관계를 저장한다. 기술 로그에는 추첨 기록 참조·신규/재사용을 남기고 Test에서 저장 결과와 대조한다.

<a id="fs-023"></a>
### FS-023 모의 상태 저장·예정 통지 실행

- **목표:** VM 없이 시간에 따른 상태·통지를 지속 처리한다.
- **목표-input:** `draw_record`: 확정된 모의 경로; `sim_state`: 현재 모의 작업/VM 상태; `due_at`: 실행할 시각 의미; `delivery_context`: 통지 대상·시도·점유.
- **목표-output:** `sim_observation`: 모의 작업/VM 조회값; `delivery_state`: 예정·전송·재전송 상태; `completion_message`: 원문 계약과 일치하는 통지 의미.
- **기능확인 Test 방식:** 시각 주입으로 예정 전후를 확인하고 dispatcher 재시작·동시 점유·대기 한도를 검사한다. HTTP 처리의 대기 sleep과 API 업무 DB 직접 수정이 없는지 확인한다.
- **기능확인 로깅 방식:** 모의 DB에 상태·예정/전송 이력을 남긴다. 기술 로그에 due 시각·사건/작업 참조·전송 결과를 기록하고 API inbox와 대조한다.

<a id="fs-024"></a>
### FS-024 성공·실패·지연·누락·중복 시나리오

- **목표:** 다섯 실행 경로를 독립적으로 재현·확인한다.
- **목표-input:** `scenario_selection`: 무작위 또는 개발 CLI 강제 경로; `profile`: 해당 경로 허용 규칙; `test_clock`: 검증용 시각 문맥.
- **목표-output:** `scenario_effect`: 정상/실패 상태·늦은 완료·통지 부재·동일 사건 재전송의 결과; `reproduction_ref`: 기대 타임라인과 연결.
- **기능확인 Test 방식:** 각 경로를 고정 fixture로 강제해 API·DB·화면을 대조한다. 누락의 재확인 상태, 늦은 완료 반영, 중복 단일 반영, 운영 강제 설정 차단을 확인한다.
- **기능확인 로깅 방식:** 기술 로그에 시나리오·추첨 참조·발생/누락/재전송 사건을 남긴다. Test 기록에 기대 타임라인·관찰 타임라인·불일치를 연결한다.

<a id="fs-025"></a>
### FS-025 모의·실제 실행환경 분리

- **목표:** 모의 자원이 실제 연동·운영 결과로 사용되지 않게 한다.
- **목표-input:** `deployment_mode`: 실행환경 구분; `adapter_selection`: 선택한 외부 구현; `data_namespace`: DB·작업·VM의 소속; `development_overrides`: 테스트 전용 설정 의미.
- **목표-output:** `mode_validation`: 기동/요청 허용 여부; `resource_boundary`: 사용할 수 있는 데이터 경계; `visible_mode`: 화면·응답·로그의 구분 정보.
- **기능확인 Test 방식:** 운영에 모의 adapter·강제 설정을 넣거나 모의 ID를 실제 경로로 전달해 차단을 확인한다. 모의 화면이 실제 SSH 가능 정보를 표시하지 않는지도 검사한다.
- **기능확인 로깅 방식:** 기술 로그·감사에 환경·adapter·소속 검사 결과를 남긴다. 자격 증명·실제 주소 없이 거부 결과와 외부 요청 없음을 대조한다.

<a id="fs-026"></a>
### FS-026 감사 원장 기록·확인

- **목표:** 주요 행위와 변경을 업무 결과에 연결해 보존한다.
- **목표-input:** `actor`: 사용자/서비스/운영 행위자; `target`: 대상 참조; `action`: 요청 작업 의미; `decision`: 허용/거부·상태 변경·근거; `transaction_context`: 업무 변경 관계.
- **목표-output:** `audit_ref`: 보존된 감사 식별; `audit_history`: 권한 있는 확인용 이력; `integrity_result`: 업무 변경과 감사 기록의 일치.
- **기능확인 Test 방식:** 성공·거부·중복·트랜잭션 실패를 확인한다. 업무 반영과 감사의 원자성, 앱 계정의 원장 수정/삭제 제한을 검사한다.
- **기능확인 로깅 방식:** 감사 원장에 행위자·대상·작업·결정·변경 의미·UTC 시각을 저장한다. Test는 업무 DB와 대조하며 기술 로그를 감사의 대체로 취급하지 않는다.

<a id="fs-027"></a>
### FS-027 기술 로그·추적·민감정보 제거

- **목표:** 사건을 추적하면서 비밀·원문 데이터 노출을 막는다.
- **목표-input:** `event_context`: 서비스·환경·release·추적·시도·사건·오류·소요 의미; `logging_policy`: 수준·제외/마스킹·출력 위치 규칙.
- **목표-output:** `structured_record`: 정책에 맞는 JSON Lines 로그; `correlation`: 요청·작업·통지의 연결; `logging_failure_signal`: 기록 장애의 확인 정보.
- **기능확인 Test 방식:** 인증·VM·통지 흐름의 로그 필드를 확인한다. 시험용 비밀·본문·주소를 입력해 노출되지 않는지 검사하고, 로그 저장 실패가 숨겨지지 않는지도 확인한다.
- **기능확인 로깅 방식:** 공통 기술 필드만 허용하고 감사 대상은 원장으로 보낸다. Test에서 비밀 노출 검색·추적 연결·오류 수준·기록 장애 결과를 별도 정제 보고서에 남긴다.

## 실제 VM 연동·동작

근거: [구조](architecture.md), [계약](contracts.md), 원문 E1·E2. G1 이후 실제 실습 Test로 확인한다. 실행 명령은 Windows 저장소가 소유한다.

<a id="fs-028"></a>
### FS-028 실제 VMM 요청·결과 adapter

- **목표:** 공통 작업 계약을 실제 VMM 수신부·공식 작업 절차와 연결한다.
- **목표-input:** `command_contract`: 허용 작업·입력·논리 대상·외부 멱등 관계; `service_auth`: 서비스 인증·권한 문맥; `real_environment`: G1에서 확인한 실행/조회 경계.
- **목표-output:** `real_receipt`: 실제 접수·외부 작업 식별; `verified_mapping`: 논리/외부 대상 연결; `integration_error`: 접수 실패·불명확·프로토콜 오류 분류.
- **기능확인 Test 방식:** 상호 TLS·출발지·최소 권한·허용 입력을 실제 수신부에서 확인한다. 정상·중복·접수 응답 유실·허용 밖 명령을 시험하고 VMM/Compute 결과와 대조한다. MSSQL 조회는 FS-018의 실제 경로로 검사한다.
- **기능확인 로깅 방식:** 기술 로그·감사에 실제 환경·서비스 역할·작업/외부 참조·판정을 남긴다. VMM·Compute 정제 증거와 연결하며 원문 명령·DB 연결정보는 제외한다.

<a id="fs-029"></a>
### FS-029 실제 VM 부팅·SSH 접근 확인

- **목표:** 생성 결과의 VM 존재·부팅·고객 접근을 각각 확인한다.
- **목표-input:** `owned_vm`: 확인할 실제 소유 자원; `boot_evidence`: Hyper-V·게스트 상태 근거; `access_policy`: 허용 사설망·고객 계정·공개키 관계; `client_observation`: 고객 단말의 접속 확인.
- **목표-output:** `creation_verification`: 실제 VM 식별·사양 일치 여부; `guest_readiness`: 게스트 확인 결과; `connection_guidance`: 소유 고객에게 제공할 접속정보 의미; `access_verification`: 실제 SSH 가능 여부.
- **기능확인 Test 방식:** 첫 회원 신청으로 생성된 별도 VM을 확인한다. 전원 동작·게스트 준비·허용 고객 SSH·다른 고객/허용 밖 접근을 나눠 시험한다. 모의 정보로 대체하지 않는다.
- **기능확인 로깅 방식:** 감사·검증 기록에 대상 참조·전원/게스트/접근의 개별 판정과 시각을 남긴다. 내부 주소·키·접속 세션 원문 없이 고객에게 표시된 정보의 적합성을 대조한다.

<a id="fs-030"></a>
### FS-030 VM 시작

- **목표:** 허용 상태의 소유 VM을 시작하고 실제 결과를 확인한다.
- **목표-input:** `vm_ref`: 실제 대상; `actor_context`: 소유/관리 권한; `current_power_state`: 작업 가능 판정 근거; `idempotency_key`: 반복 제출 식별.
- **목표-output:** `start_job`: 접수된 시작 작업; `confirmed_power_state`: 확인된 전원 결과; `guest_observation`: 별도 게스트 준비 의미; `failure_reason`: 불가/실패 이유.
- **기능확인 Test 방식:** 시작 가능한 상태·이미 실행 중·타인 요청·반복 제출·실행 실패를 시험하고 Hyper-V의 관찰값과 비교한다. 전원 확인을 게스트 준비로 간주하지 않는다.
- **기능확인 로깅 방식:** 감사에 행위자·VM·시작 요청·확인 전후 상태를 남긴다. 작업/시도 추적과 Hyper-V·게스트 증거를 각각 연결한다.

<a id="fs-031"></a>
### FS-031 VM 중지

- **목표:** 정해진 종료 정책으로 VM을 중지하고 결과를 확인한다.
- **목표-input:** `vm_ref`: 실제 대상; `actor_context`: 실행 권한; `stop_policy`: 지원되는 종료 방법·예외 처리 의미; `current_power_state`: 실제 상태; `idempotency_key`: 제출 식별.
- **목표-output:** `stop_job`: 접수된 중지 작업; `confirmed_stop`: 실제 종료 판정; `stop_exception`: 미종료·거부·재확인 이유.
- **기능확인 Test 방식:** 정상 종료·이미 중지·종료 지연·타인 요청·중복을 확인한다. 강제 종료 여부는 확정한 정책에 따라 검사하고, 중지 시간이 청구 기간에서 제거되지 않는지도 확인한다.
- **기능확인 로깅 방식:** 감사에 종료 방법의 분류·대상·요청/확인 시각·결과를 남긴다. 실제 전원 관찰과 작업 기록을 대조한다.

<a id="fs-032"></a>
### FS-032 VM 재시작

- **목표:** 허용된 VM을 재시작하고 재기동 결과를 확인한다.
- **목표-input:** `vm_ref`: 대상; `actor_context`: 실행 권한; `restart_policy`: 현재 상태별 지원 방법·준비 확인 조건; `idempotency_key`: 제출 식별.
- **목표-output:** `restart_job`: 재시작 작업; `restart_observation`: 재기동 전후 실제 상태·시각; `readiness_result`: 게스트 재확인 여부; 오류/보류 이유.
- **기능확인 Test 방식:** 가능한 상태·불가 상태·게스트 재기동 지연·반복·실패를 시험한다. 기존 실행 상태를 재시작 완료로 오인하지 않고 실제 시도 근거를 확인한다.
- **기능확인 로깅 방식:** 감사에 재시작 대상·방법 분류·시도·실제 관찰 시각을 남긴다. 게스트 재확인과 작업 완료 증거를 분리해 연결한다.

<a id="fs-033"></a>
### FS-033 VM 삭제·잔여 디스크 처리

- **목표:** 삭제 정책에 따라 자원을 처리하고 확인 시점·잔여물을 기록한다.
- **목표-input:** `vm_ref`: 삭제 대상; `actor_context`: 실행 권한; `deletion_confirmation`: 대상·영향 확인 의미; `disk_policy`: 확정할 삭제/보존/정리 조건; `idempotency_key`: 제출 식별.
- **목표-output:** `delete_job`: 삭제 작업; `deletion_observation`: 실제 VM 삭제 판정·시각; `residual_resources`: 정리/보존/복구가 필요한 디스크 참조; `billing_boundary`: 확인된 사용 종료 근거.
- **기능확인 Test 방식:** 정상·중복·이미 없어진 VM·부분 삭제·남은 디스크·타인 요청을 확인한다. 정책 확정 후 실제 파일 상태를 대조하고 삭제 접수만으로 청구가 종료되지 않는지 검사한다.
- **기능확인 로깅 방식:** 감사에 삭제 영향 확인·실제 삭제·디스크 처리 분류·잔여 참조·시각을 남긴다. 전체 경로를 공개하지 않고 정리/복구 증거를 연결한다.

<a id="fs-034"></a>
### FS-034 VM 사양 변경·적용 이력

- **목표:** 지원 조건에서 변경하고 실제 적용 사양과 시각을 보존한다.
- **목표-input:** `vm_ref`: 대상; `target_profile`: 원하는 허용 사양; `current_spec_and_power`: 현재 적용값·전원 상태; `change_policy`: 지원 조건·실패 원복 의미; `actor_context`: 권한.
- **목표-output:** `change_job`: 변경 작업; `applied_spec_revision`: 확인된 실제 사양·버전·시각; `rollback_or_pending`: 실패 후 실제 결과와 미확정 이유; 청구 구간 변경 근거.
- **기능확인 Test 방식:** 지원/불가 전원 상태·잘못된 사양·부분 적용·원복 실패·중복을 확인한다. 요청 사양과 실제 적용값을 구분하고, 실패한 요청으로 청구 이력이 바뀌지 않는지 검사한다.
- **기능확인 로깅 방식:** 감사에 이전/실제 적용 사양의 정제 요약·변경 시각·작업/시도·원복 결과를 남긴다. Hyper-V 확인과 청구 구간 근거를 연결한다.

## 가상 사용량·청구

근거: 원문 E3와 [단계별 범위](../implementation-scope.md). 단가·반올림·청구 상태의 실제 정책은 설계·검증 후 정하며 실금전 청구를 추가하지 않는다.

<a id="fs-035"></a>
### FS-035 가상 단가·반올림 버전 관리

- **목표:** 청구 당시 계산 규칙을 나중에도 재현한다.
- **목표-input:** `pricing_definition`: 사양별 가상 단가·과금 단위 의미; `rounding_policy`: 반올림 시점·방법·단위 의미; `effective_period`: 적용 기간; `policy_authority`: 규칙 관리 권한.
- **목표-output:** `pricing_version`: 불변 계산 규칙 식별; `validated_rules`: 계산 가능한 규칙; `policy_errors`: 기간 충돌·잘못된 단위·불가 정의.
- **기능확인 Test 방식:** 기간 경계·규칙 오류·버전 변경을 확인하고 과거 청구가 신규 규칙으로 덮어써지지 않는지 검사한다. 금액 계산은 Decimal 경계와 반올림 사례로 확인한다.
- **기능확인 로깅 방식:** 감사에 규칙 버전·적용 기간·변경 종류·판정을 남긴다. Test에는 계산식 의미와 재현 버전을 연결하고 실제 단가 예제를 공개하지 않는다.

<a id="fs-036"></a>
### FS-036 실제 적용 사양별 사용 구간

- **목표:** 실제 생성부터 삭제까지 사양 변경 기준으로 사용 기간을 나눈다.
- **목표-input:** `verified_lifecycle`: 실제 생성/삭제 확인 시각; `applied_spec_history`: 실제 적용 사양·변경 시각; `period_context`: UTC 원장과 청구 시간대 관계.
- **목표-output:** `usage_segments`: 연속 사용 기간·실제 사양 관계; `segment_boundaries`: 분할 근거; `incomplete_evidence`: 미확정 경계의 보류 이유.
- **기능확인 Test 방식:** 생성·월 경계·중지·사양 변경·삭제·동일 사건 재실행을 검사한다. 중지 시간 포함, 구간 겹침/누락 방지, 요청 시각 대신 확인 시각 사용을 확인한다.
- **기능확인 로깅 방식:** 원장에 구간·사양/사건 참조·경계 근거를 저장한다. 기술 로그는 신규/재사용/보류를 남기고 수명주기 감사와 대조한다.

<a id="fs-037"></a>
### FS-037 전월 청구서 발행·중복 방지

- **목표:** 정해진 월 실행에서 전월 사용분을 중복 없이 계산·발행한다.
- **목표-input:** `billing_month`: 대상 사용 월; `usage_segments`: 확인된 구간; `pricing_versions`: 적용할 가상 규칙; `run_context`: 정기/재실행 구분과 권한.
- **목표-output:** `invoice_ref`: 회원·월 청구 식별; `line_items`: 구간별 계산 근거; `total_and_status`: 계산 결과·발행 상태 의미; `issuance_resolution`: 신규/기존/보류 판정.
- **기능확인 Test 방식:** 청구 시간대 월 경계·사양 변경·삭제·규칙 버전·동시/재실행을 확인한다. 회원·월 고유 제약과 불완전 사용 근거의 발행 보류를 검사한다.
- **기능확인 로깅 방식:** 원장·감사에 발행 실행·대상 월·구간/규칙 버전·청구 참조·중복/보류를 남긴다. Test는 항목 합계와 구간별 계산 근거를 대조한다.

<a id="fs-038"></a>
### FS-038 청구서 조회·상태 관리

- **목표:** 소유 범위의 계산 근거와 청구 상태를 보여주고 허용 변경을 관리한다.
- **목표-input:** `actor_context`: 회원/관리자 권한; `invoice_ref`: 대상; `query_scope`: 기간·상태·목록 범위; `state_action`: 정책상 허용된 상태 변경의 의미.
- **목표-output:** `invoice_view`: 기간·구간·사양·단가 버전·계산 결과·상태 의미; `state_history`: 허용 변경 이력; `denial_or_pending`: 거부/보류 이유.
- **기능확인 Test 방식:** 회원 본인/관리자 전체·타인 차단·근거 펼침·불가 상태 전이를 확인한다. 테스트 PG를 연결하지 않아도 생성·조회·상태 관리 범위가 유지되는지 검사한다.
- **기능확인 로깅 방식:** 기술 로그에 조회 범위·청구 참조를, 감사에 상태 변경 행위자·전후 의미·근거를 남긴다. 공개 증거에는 개인 청구 상세를 정제한다.

## 인프라 관찰·실습·제어

근거: 원문 E0·E4, [단계](stages.md), [UI 가이드](../ui/guide.md). 네트워크·DB 이중화·정족수·executor 기술의 미정 선택을 임의 확정하지 않는다.

<a id="fs-039"></a>
### FS-039 Windows 인프라 상태·검증 기록

- **목표:** 관리자 콘솔에서 Windows 호스트·VM의 실습 상태와 검증 이력을 확인한다.
- **목표-input:** `admin_context`: 조회 권한; `infra_refs`: 등록한 호스트/노드/VM 참조; `observations`: 정제 상태·시각·장애 정보; `verification_records`: 실행 조건·증거·한계.
- **목표-output:** `infrastructure_view`: 역할·상태·마지막 확인·문제; `verification_history`: 성공/실패/미실행과 근거; `scope_limitations`: 실제 확인한 장애 범위.
- **기능확인 Test 방식:** 정상·장애·오래된 값·증거 없음·회원 접근 거부를 확인한다. Windows 저장소의 실제 결과와 화면을 비교하고 모의/실제와 지원성/동작 성공을 구분한다.
- **기능확인 로깅 방식:** 기술 로그에 관찰 수집/조회·대상 참조·신선도·오류를 남긴다. Test는 정제 호스트 증거와 화면 표시를 연결한다.

<a id="fs-040"></a>
### FS-040 인프라·Linux 별도 검증·보존 축소

- **목표:** 정해진 실습 단계를 분리하고 VM·디스크를 보존해 최소 서비스로 전환한다.
- **목표-input:** `approved_topology`: 확정 역할·대수·계층; `resource_evidence`: 자원·제품 사용 권한·지원성; `test_plan`: Compute 단독/클러스터/Linux 이중화 순서와 합격 조건; `preservation_plan`: 보존 전환 방법.
- **목표-output:** `stage_evidence`: 각 환경의 실제 검증 결과; `preserved_resources`: 이관 전후 VM·디스크 참조/일치; `active_topology`: 축소 후 가동·자동 시작 제한 상태; `blockers`: 불충족 조건.
- **기능확인 Test 방식:** 두 대규모 검증을 동시에 진행하지 않고 각 단계의 장애·전환을 시험한다. Linux 콘솔/API VIP·MySQL의 선정된 복제/전환과 세션·작업 중복 방지, 인프라 보존 축소·호스트 재부팅 후 제한을 확인한다.
- **기능확인 로깅 방식:** 운영 검증 기록에 단계·선정 기술·자원 근거·이관 목록 참조·전후 결과·한계를 남긴다. 실제 VM/디스크 관찰을 연결하며 단일 호스트 실험을 물리 장애 내성으로 표시하지 않는다.

<a id="fs-041"></a>
### FS-041 Linux·DB·접근 경로 상태 관찰

- **목표:** 서비스 MySQL과 별도 MariaDB/Galera·접근 경로 상태를 구분해 관찰한다.
- **목표-input:** `infra_inventory`: 등록 노드·서비스·역할; `observation_sources`: 허용 상태 조회 경계; `quorum_definition`: 사용자 선정 정족수 조건; `admin_context`: 조회 권한.
- **목표-output:** `linux_observations`: 노드·DB·정족수·Nginx/Keepalived 경로 상태·시각; `freshness_and_errors`: 오래됨/관찰 실패; `service_separation`: MySQL 업무 서비스와 Galera 실습 구분.
- **기능확인 Test 방식:** 노드/서비스 장애·관찰 실패·VIP 전환·정족수 상실을 시험해 실제 결과와 대조한다. Galera 성공을 서비스 MySQL의 이중화 성공으로 표시하지 않는지 확인한다.
- **기능확인 로깅 방식:** 기술 로그에 역할·대상 참조·관찰 항목·시각·오류/변화를 남긴다. 실제 서비스 검증 증거와 연결하고 내부 주소·접속 비밀을 제외한다.

<a id="fs-042"></a>
### FS-042 허용 Linux 제어·장애 복구 확인

- **목표:** 관리자 허용 작업만 실행하고 장애·재합류·경로 복구를 확인한다.
- **목표-input:** `admin_context`: 실행 권한; `target_ref`: 등록 대상; `allowed_operation`: 선정 executor의 허용 작업; `validated_parameters`: 제한 입력; `recovery_policy`: 장애·재합류·실패 처리 조건.
- **목표-output:** `control_job`: 제어 작업; `verified_control_result`: 실제 변경/복구·관찰 시각; `consistency_evidence`: 데이터·경로 일관성 결과; `failure_or_remaining`: 실패·잔여 복구 대상.
- **기능확인 Test 방식:** 임의 명령·무허가/미등록 대상 차단, 데이터 노드 중지·재합류·동시 수정/삭제·네트워크 분리·경로 전환을 정해진 합격 조건으로 확인한다.
- **기능확인 로깅 방식:** 감사에 관리자·대상·허용 동작·작업 결과를 남긴다. 검증 기록은 데이터 일관성·충돌·재합류·경로 관찰 근거를 연결하고 전체 명령·데이터 원문은 제외한다.

<a id="fs-043"></a>
### FS-043 VPC 분리·연결·제어

- **목표:** 선택한 기술로 시험 네트워크의 분리/연결과 허용 제어를 검증한다.
- **목표-input:** `vpc_refs`: 등록 시험 네트워크; `connectivity_policy`: 허용/차단 통신 관계; `requested_transition`: 분리/연결 동작 의미; `admin_context`: 권한; `implementation_choice`: 사용자 선정 구현/제어 방식.
- **목표-output:** `vpc_job`: 제어 작업; `observed_connectivity`: 실제 통신 가능/차단·시각; `applied_policy`: 확인된 규칙 상태; `recovery_result`: 실패 후 복구 여부.
- **기능확인 Test 방식:** 분리 시 차단·연결 시 허용·허용 밖 경로 차단·무허가 요청·부분 적용/복구를 양쪽 네트워크에서 확인한다. 기술 미정 상태에서는 실습 통과로 기록하지 않는다.
- **기능확인 로깅 방식:** 감사에 네트워크 참조·정책 버전·변경 행위·결과를 남긴다. 정제 통신 Test 결과를 연결하고 내부 주소·전체 방화벽 설정을 공개하지 않는다.

## 알림·조건부 연동

근거: 원문 E4 및 최신 PMT 알림·조건부 범위. Prototype에는 외부 발송을 추가하지 않는다.

<a id="fs-044"></a>
### FS-044 Slack 알림

- **목표:** 선정 사건을 허용된 시험 목적지로 전달하고 실패를 추적한다.
- **목표-input:** `notification_event`: 작업/장애/운영 알림의 정제 의미; `destination_ref`: 등록 목적지 참조; `notification_policy`: 선정 사건·중복 억제·재시도 조건.
- **목표-output:** `delivery_ref`: 발송 시도 식별; `delivery_result`: 전달/실패/보류 의미; `retry_state`: 재시도/중복 억제 상태.
- **기능확인 Test 방식:** 정상·목적지 오류·외부 장애·같은 사건 반복을 시험한다. 목적지는 허용 설정을 사용하고, 알림 실패가 VM 성공을 되돌리지 않는지 확인한다.
- **기능확인 로깅 방식:** 기술 로그/발송 원장에 사건·목적지 참조·시도·결과·오류를 남긴다. webhook·토큰·메시지 원문 없이 외부 전달 확인과 대조한다.

<a id="fs-045"></a>
### FS-045 제한 이메일 시험

- **목표:** 임시 메일 환경의 허용 수신자에게만 시험 메시지를 보낸다.
- **목표-input:** `message_event`: 정제 알림 의미; `recipient_ref`: 허용 주소 목록과 연결된 수신자; `mail_test_environment`: 임시 서버·발송 정책 의미.
- **목표-output:** `mail_attempt`: 발송 시도; `mail_delivery_state`: 접수·배달 확인·실패·거부 구분; `recipient_validation`: 허용 수신자 판정.
- **기능확인 Test 방식:** 허용/비허용 수신자·서버 장애·반복 사건을 확인한다. 서버 접수와 실제 수신을 분리해 확인하고 범위 밖 발송을 차단한다.
- **기능확인 로깅 방식:** 기술 로그/발송 원장에 수신자 참조·허용 검사·접수/수신 확인·시도를 남긴다. 주소·비밀번호·메일 본문은 정제하고 수신 증거를 연결한다.

<a id="fs-046"></a>
### FS-046 SMS 시험 가능성·조건부 연동

- **목표:** 공식 시험 환경 가능성을 확인하고 조건 충족 시에만 연동한다.
- **목표-input:** `official_test_capability`: 공식 테스트 지원·사용 조건 근거; `allowed_recipient_policy`: 시험 수신 범위; `implementation_decision`: 구현/보류 결정; 조건 충족 시 정제 발송 사건.
- **목표-output:** `sms_scope_decision`: 구현/보류와 근거; 조건 충족 시 `sms_delivery_state`: 발송 시도·결과 의미.
- **기능확인 Test 방식:** 공식 환경·허용 수신·시험/실발송 경계를 확인한다. 가능하면 정상/실패 발송을 검사하고, 미확보면 조건 대기/보류를 기록한다. 구현 여부를 자동 확정하지 않는다.
- **기능확인 로깅 방식:** 결정 기록에 근거·범위·판정을, 구현 시 발송 원장에 정제 수신자 참조·시도·결과를 남긴다. 전화번호·키·본문은 제외한다.

<a id="fs-047"></a>
### FS-047 테스트 PG 가능성·조건부 연동

- **목표:** 공식 테스트 환경 조건을 확인하고 가상 청구의 시험 상태만 연결한다.
- **목표-input:** `official_pg_test_capability`: 공식 시험 사용 가능 근거; `test_invoice_ref`: 시험 청구 대상; `test_payment_context`: 시험 주문·결과의 관계; `implementation_decision`: 연동/대체 범위 결정.
- **목표-output:** `pg_scope_decision`: 테스트 연동 또는 자체 청구 상태 관리의 근거; 조건 충족 시 `test_payment_result`: 시험 처리·취소/실패와 청구 상태 연결.
- **기능확인 Test 방식:** 테스트 자격·중복 결과·실패/취소·다른 청구 연결을 확인한다. 실제 결제 경로를 실행하지 않으며 조건 불충족 시 FS-038로 범위를 유지한다.
- **기능확인 로깅 방식:** 결정 기록·감사에 시험환경·청구/시험 거래의 정제 참조·중복·상태 결과를 남긴다. 결제키·개인/카드 정보는 기록하지 않는다.

<a id="fs-048"></a>
### FS-048 로그 회전·보존·원장 정리

- **목표:** 제한된 저장공간에서 기술 로그를 관리하고 활성 원장을 보호한다.
- **목표-input:** `retention_policy`: 기록별 보존·회전·용량·archive 조건; `record_inventory`: 파일/원장의 시각·크기·활성 여부; `cleanup_authority`: 정리용 권한.
- **목표-output:** `rotation_archive_result`: 회전·압축·재열기·보관 결과; `cleanup_report`: 삭제/보호 대상과 이유; `capacity_signal`: 공간 부족·접수 제한 필요성.
- **기능확인 Test 방식:** 기간/크기 경계·회전 후 기록 지속·파일 권한·archive 실패를 확인한다. 활성/재확인 작업·감사/청구 원장의 무단 유실을 막는지 검사한다.
- **기능확인 로깅 방식:** 운영 로그에 정책 참조·정리 대상 종류·처리량·오류·보호 이유를 남긴다. 정리 전후 목록·원장 및 공간 경보 증거를 대조한다.

<a id="fs-049"></a>
### FS-049 서비스·작업 감시·경보

- **목표:** 중단·대기·오류·용량·백업·인증서 문제를 탐지한다.
- **목표-input:** `health_observations`: 서비스·worker 생존·작업 지연·오류·디스크·백업 시각·인증서 상태; `alert_policy`: 판정·중복 억제·복구 해제 조건; `destination_refs`: 허용 알림 경로.
- **목표-output:** `health_assessment`: 정상/문제·근거; `alert_state`: 발송 필요·중복 억제·해제; `operational_issue_ref`: 추적 가능한 운영 문제.
- **기능확인 Test 방식:** worker 종료·callback 누락·DB 실패·공간 부족·백업/인증서 기준 초과를 주입하고 탐지·억제·복구 해제를 확인한다. 감시 경로 자체 실패도 확인한다.
- **기능확인 로깅 방식:** 기술 로그에 관찰 항목·정책 참조·상태 변화·알림 시도를 남긴다. 문제 발생/탐지/해제 시각과 FS-044~045 결과를 연결한다.

<a id="fs-050"></a>
### FS-050 인증서 갱신·비밀정보 권한 관리

- **목표:** 등록 서비스의 신뢰·비밀 접근을 유지하고 교체를 검증한다.
- **목표-input:** `service_identity_map`: 서비스·인증서·권한의 관계; `trust_policy`: 서버/클라이언트 신뢰·허용 출발지 의미; `renewal_policy`: 갱신·폐기·오프라인 CA 운영 조건; `secret_access_policy`: 서비스 계정별 읽기 범위.
- **목표-output:** `trust_validation`: 신원·체인·사용 용도·접속 검증; `rotation_result`: 교체/갱신과 서비스 재확인; `access_validation`: 허용/거부 계정 결과.
- **기능확인 Test 방식:** 만료/잘못된 신뢰·다른 서비스 인증서·미등록 출발지·비인가 계정 읽기·갱신 후 요청/통지를 실제 시험한다. 기존 키/CA 재사용은 적합성 확인 뒤 검증한다.
- **기능확인 로깅 방식:** 보안 감사에 인증서의 정제 참조·서비스 역할·검사 항목·교체/권한 결과를 남긴다. 개인키·비밀 파일 내용 없이 통신 전후 증거를 연결한다.

<a id="fs-051"></a>
### FS-051 재부팅 후 서비스 기동·가동 대수

- **목표:** 의존 조건에 따라 최소 서비스를 기동하고 추가 VM 자동 시작을 제한한다.
- **목표-input:** `service_topology`: 확정 최소 가동 역할; `startup_dependencies`: AD/DNS·저장·Compute·Linux DB/API/콘솔 준비 관계; `autostart_policy`: 추가 VM 제한; `host_restart`: 재부팅 사건.
- **목표-output:** `startup_assessment`: 실제 기동·준비 여부; `active_inventory`: 가동/종료 VM 역할; `dependency_errors`: 준비 실패·잘못된 자동 시작.
- **기능확인 Test 방식:** 호스트 재부팅·의존 서비스 지연/실패 후 가동 상태를 확인한다. 역할별 준비 확인 전에 고객 작업을 받지 않는지, 추가 VM이 자동 시작하지 않는지 검사한다.
- **기능확인 로깅 방식:** 운영 기록에 재부팅·역할별 기동/준비 시각·가동 목록 참조·실패를 남긴다. 실제 호스트 관찰과 서비스 health를 대조한다.

<a id="fs-052"></a>
### FS-052 DB·설정·고객 VM 백업

- **목표:** 일관된 복원에 필요한 데이터를 별도 매체에 보존한다.
- **목표-input:** `backup_scope`: 업무 DB·필요 설정·고객 VM/디스크의 관계; `consistency_policy`: 정합성 확보 방법; `destination_ref`: 별도 매체 참조; `backup_policy`: 주기·보존·권한·확인 조건.
- **목표-output:** `backup_set_ref`: 관련 데이터가 연결된 백업 집합; `integrity_evidence`: 완전성·일관성 확인; `backup_result`: 성공·미완료·실패 이유와 시각.
- **기능확인 Test 방식:** 정상·매체 불가·중간 실패·변경 중 데이터의 일관성을 검사한다. 완료 표시가 실제 복원 가능한 집합을 뜻하는지 FS-053으로 확인하고 비밀 보관 경계도 검사한다.
- **기능확인 로깅 방식:** 운영 감사에 백업 범위 참조·집합·시각·완전성·매체 오류를 남긴다. 민감한 경로/데이터 없이 파일·DB 검증 근거와 복원 Test를 연결한다.

<a id="fs-053"></a>
### FS-053 DB·고객 VM 복원·복구 검증

- **목표:** 백업으로 업무 상태와 고객 접근을 실제 복구한다.
- **목표-input:** `backup_set_ref`: 복구 집합; `restore_scope`: 복원 대상과 영향; `recovery_target`: 복구 가능한 데이터 시점·시간 목표의 의미; `restore_authority`: 승인된 복구 작업 문맥.
- **목표-output:** `restored_state`: DB·작업 매핑·VM/디스크 복원 결과; `access_result`: 복구 VM 접근 확인; `measured_recovery`: 데이터 손실 구간·소요시간; `unresolved_items`: 미복구 대상.
- **기능확인 Test 방식:** 격리된 복원 환경에서 DB·VM·파일 관계, 게스트 부팅/SSH, 누락·불일치 백업을 확인한다. 측정 결과를 확정한 복구 목표와 비교하고 운영 원본을 훼손하지 않는다.
- **기능확인 로깅 방식:** 운영 감사에 집합·복원 대상 참조·시작/완료·무결성·접근·미복구 의미를 남긴다. 복구 전후 증거와 목표 대비 측정을 연결한다.

<a id="fs-054"></a>
### FS-054 릴리스 배포·롤백

- **목표:** 잠금된 배포물을 검증해 적용하고 실패 시 확인된 이전 상태로 전환한다.
- **목표-input:** `release_artifact`: 코드·의존성·체크섬·manifest 관계; `deployment_config`: 대상 환경·서비스 역할; `migration_plan`: DB 호환성·복원 조건; `rollback_target`: 이전 배포 연결.
- **목표-output:** `deployment_state`: 적용 release·health·migration 결과; `rollback_result`: 이전 코드 전환·DB 적합성·서비스 재확인; `deployment_blockers`: 안전한 진행 불가 이유.
- **기능확인 Test 방식:** 정상 배포·health 실패·중간 중단·롤백·DB 호환/불가 변경을 시험한다. 복원 절차 없는 파괴적 migration과 운영 모의 설정을 차단한다.
- **기능확인 로깅 방식:** 운영 감사에 이전/대상 release·검사 단계·migration 참조·전환/차단·health를 남긴다. 서비스 응답과 배포물 체크섬을 대조하며 비밀 설정은 제외한다.

<a id="fs-055"></a>
### FS-055 운영 부하·용량·한도 확인

- **목표:** 실측으로 운영 가능한 회원·VM·동시 작업·요청 한도를 판정한다.
- **목표-input:** `load_profile`: 시험 요청·동시 작업·자원 조합의 의미; `resource_budget`: 실제 CPU/RAM/디스크 여유; `acceptance_policy`: 허용 지연·오류·용량 기준; `test_scope`: 모의/실제 환경 구분.
- **목표-output:** `measurement_report`: 처리·지연·오류·자원·대기 변화; `capacity_assessment`: 목표 충족/제한 이유; `recommended_limits`: 근거 있는 운영 한도.
- **기능확인 Test 방식:** 기준·경계·한도 초과·장기 대기·회복을 실제 해당 환경에서 측정한다. 모의 처리량을 실제 VM 처리량으로 표현하지 않고 미정 기준은 대기로 남긴다.
- **기능확인 로깅 방식:** 측정 기록에 프로필/환경·시각·release·관찰값·판정을 남긴다. 작업 로그·감시 지표와 대조하고 원본 개인 요청은 정제한다.

<a id="fs-056"></a>
### FS-056 기능검증 증거·공개자료 정리

- **목표:** 기능별 합격 근거·재현 방법·한계를 민감정보 없이 남긴다.
- **목표-input:** `feature_test_records`: 기능 ID·사례·기대/관찰·결과; `source_evidence`: 로그·DB·화면·외부 확인 자료; `redaction_policy`: 공개 제외 기준; `runtime_context`: 환경·release·설정/알고리즘 버전 참조.
- **목표-output:** `verified_evidence_refs`: 정제된 근거 위치; `coverage_report`: 실행·실패·미실행·조건 대기 기능; `reproduction_notes`: 재현 순서·전제·검증 한계.
- **기능확인 Test 방식:** 기능목록과 Test/증거 ID를 대조하고 누락·깨진 링크·모의/실제 혼동·민감정보 노출을 검사한다. 재현 조건이 없는 성공 표시를 거부한다.
- **기능확인 로깅 방식:** 정제 보고서에 기능/사례 식별·자료 출처 종류·검사·결과·정제 여부를 남긴다. 원본 운영 로그를 Git에 넣지 않고 기술 로그·감사·실습 근거를 각각 참조한다.

<a id="fs-057"></a>
### FS-057 DB 스키마 구성·마이그레이션

- **목표:** 업무·세션·작업·감사와 모의 저장소를 버전 관리된 구조로 준비한다.
- **목표-input:** `migration_set`: 해당 release의 schema 변경 정의·순서; `current_schema_revision`: 현재 적용 이력; `database_role`: 업무/모의 저장소 구분과 전용 권한; `migration_authority`: 구조 변경 실행 문맥.
- **목표-output:** `applied_schema_revision`: 실제 적용 구조 버전; `migration_result`: 적용/기존/실패·보류 의미; `constraints_and_permissions`: 외래키·고유 제약·계정 경계의 확인 결과.
- **기능확인 Test 방식:** 빈 테스트 DB·기존 구조·재실행·중간 실패·잘못된 순서·권한 부족을 확인한다. 세션 공유와 멱등 제약, 모의 계정의 업무 DB 접근 차단을 검사한다. 기존 데이터 변경은 FS-054의 호환 정책을 적용한다.
- **기능확인 로깅 방식:** 운영/기술 로그에 migration 참조·구조 버전 전후·DB 역할·적용/실패를 남긴다. 연결 비밀·SQL 본문 없이 schema·제약·권한 Test 결과를 연결한다.

<a id="fs-058"></a>
### FS-058 콘솔 API 프록시·신뢰 헤더

- **목표:** 콘솔의 같은 출처 경로로 API를 연결하고 위조 신원·출처를 신뢰하지 않는다.
- **목표-input:** `browser_request`: 등록 콘솔의 경로·방식·세션/CSRF 전송 문맥; `proxy_routes`: 콘솔/API의 허용 경로 관계; `trusted_proxy_policy`: 신뢰할 중계 주체와 Host/scheme/추적 헤더 처리 의미.
- **목표-output:** `forwarded_request`: 정해진 API 경로·검증된 중계 문맥; `browser_response`: API 결과와 해당 콘솔의 쿠키/보안 메타데이터; `routing_rejection`: 미등록 경로·위조 문맥 거부 이유.
- **기능확인 Test 방식:** 두 콘솔의 로그인/API 호출·cookie/CSRF 경계를 브라우저에서 확인한다. 미등록 Host·위조 전달/인증 헤더·직접 API 접근을 시험하고 등록 프록시 밖의 신뢰 헤더를 무시/거부하는지 검사한다.
- **기능확인 로깅 방식:** 접근/기술 로그에 콘솔 역할·정규화된 경로·요청 추적·라우팅/신뢰 판정을 남긴다. 쿠키·헤더 비밀·query string 없이 API 로그와 연결한다.

## 검증 연결과 미정 사항

- 기능별 Test 사례는 기능 ID에 정상·거부·경계·장애·재실행의 사례 식별을 붙여 관리한다. 적용하지 않는 사례는 이유를 기록한다.
- 종단 확인은 인증·CSRF·소유권 → 사양 → 신청/멱등 → outbox/worker → 모의 추첨/예정 통지 → inbox/전이 → 상태/화면 → 감사/기술 로그를 연결한다.
- 실제 확장은 같은 작업 계약과 실제 VMM·MSSQL·Hyper-V·게스트 증거를 연결하고, 이후 사양 이력·사용 구간·청구·인프라·알림을 검증한다.
- 미정: 실습 자원/라이선스·네트워크·IIS 기술·MSSQL 대상·실제 복구/디스크 정책·MySQL 이중화·Galera 정족수/배치·VPC·알림 사건·조건부 연동·운영 한도/보존/복구 수치. 해당 단계 전 확정 후 Test 기준을 보완한다.
- 이 문서의 완료는 **기능명세 작성 완료**다. 기능 동작 완료는 구현 후 Test 결과와 로그/원장/외부 관찰 근거가 있어야 기록한다.
